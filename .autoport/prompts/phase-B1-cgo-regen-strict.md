# Phase B1 — Re-emit jak1 CGOs with the now-complete arm64 emitter

## What this phase delivers

A fresh set of **arm64 jak1 CGOs** generated by `build-arm64/goalc/goalc`
(post-A4, with full encoder coverage + working linker fix-ups),
written to a dedicated arm64-CGO location, leaving the **x86 CGOs at
`out/jak1/iso/` byte-identical** to their pre-B1 state (the desktop
oracle still depends on them).

Plus a structural-check report
(`.autoport/reports/B1-cgo-structure.json`) proving each arm64 CGO:
- has a sane file size (within the same order of magnitude as its
  x86 sibling)
- contains many `0xd65f03c0` (arm64 `ret`) instructions and very few
  `0xc3` (x86 `ret`) bytes (a cross-arch contamination smell)
- decodes cleanly via `aarch64-linux-gnu-objdump` on a representative
  function extracted via `.autoport/lib/cgo_inspect.py`
- has gcommon's link-table walkable by the same probe A4 introduced
  (so the relocations the A4 linker emitted are still valid in a
  full-jak1 build, not just the synthetic tests A3 used)

## Why this matters

A2 wrote the encoders. A3 proved per-IR correctness with synthetic
tests. A4 wired the link-fixups and verified one symbol via a kernel
probe. **B1 is the first end-to-end exercise of the full pipeline on
the real jak1 source.** If A2-A4 are right, this should "just work."
If there's a bug, it'll show up as a CGO with the wrong size,
malformed bytes, or an unwalkable link table.

Bucket B's stretch goal — B2 — runs decode-stress under qemu over
every function in every CGO. B1 establishes that the *files
themselves* are well-formed, before B2 spends CPU testing each
function.

## Concrete deliverables

### 1. Regen flow with x86-CGO preservation

A driver script `.autoport/lib/build_b1_arm64_cgos.sh` that:

1. **Snapshots** the existing x86 CGOs:
   `cp out/jak1/iso/{KERNEL,ENGINE,GAME}.CGO .autoport/backups/B1-x86-cgos/`
   then records their sha256 hashes to
   `.autoport/reports/B1-x86-baseline.txt`.

2. **Rebuilds** `build-arm64/goalc/goalc` so it picks up A4's
   ObjectGenerator changes (if anything in the working tree drifted
   since A4's binary was compiled): `cmake --build build-arm64
   --target goalc -j8`.

3. **Runs `(mi)`** with the arm64 goalc, producing CGOs at
   `out/jak1/iso/` (where the goalc tooling writes by default):
   `build-arm64/goalc/goalc --user-auto --game jak1 --disable-ansi -c "(mi)"`.
   Banner "Successfully built all N targets" must appear.

4. **Relocates** the arm64 CGOs to a dedicated location so the
   x86-build assumption (`out/jak1/iso/` holds the x86 set) is
   restored:
   `mv out/jak1/iso/{KERNEL,ENGINE,GAME}.CGO out/jak1-arm64/iso/`.
   Record their sha256 hashes to
   `.autoport/reports/B1-arm64-cgos.txt`.

5. **Restores** the x86 CGOs by running x86 `(mi)`:
   `build/goalc/goalc --user-auto --game jak1 --disable-ansi -c "(mi)"`.
   Re-hash and verify against
   `.autoport/reports/A2-baseline-x86-cgo-hashes.txt` — must be
   byte-identical (the same source compiled the same way produces
   the same bytes; if not, something in shared code drifted).

The script must be **idempotent** — running it twice produces the
same arm64 CGOs (same bytes, same hashes). The validator runs it
twice for the reproducibility check.

### 2. Structural-check tooling

`.autoport/lib/cgo_structure_check.py` reads one CGO and reports:

- `total_bytes` — file size.
- `arm64_ret_count` — bytes containing `0xd65f03c0` (any of 4
  possible 4-byte alignments, the script just counts matches anywhere
  for robustness).
- `x86_ret_count` — bytes equal to `0xc3` (single-byte, much more
  permissive, but arm64-emitted code should still have low density).
- `ret_density_per_kb` — `arm64_ret_count * 1024 / total_bytes`.
- `min_function_size`, `max_function_size`, `mean_function_size` —
  derived from cgo_inspect.py's v3 parser.
- `decode_sample` — a snippet of `aarch64-linux-gnu-objdump -d` on
  the first function extracted from the CGO; mnemonic histogram
  (`stp`, `ldp`, `mov`, `ret`, `ldr`, `str`, etc.) for sanity.

Output: `.autoport/reports/B1-cgo-structure.json` with one entry per
CGO.

### 3. Re-run A4's kernel probe against the new KERNEL.CGO

Just confirm the new arm64 KERNEL.CGO still produces a stable nonzero
digest from the A4 probe — proves the link table is intact end-to-end
when produced by the full pipeline. Output appended to
`.autoport/reports/B1-kernel-probe.txt` (a separate file from A4's
because the value may differ if jak1's symbol-table layout
shifted; B1 just needs nonzero and reproducible across two runs).

### 4. Markdown summary

`.autoport/reports/B1-cgo-structure.md` with the headline:

> arm64 CGOs regenerated: KERNEL.CGO=<N>B, ENGINE.CGO=<M>B,
> GAME.CGO=<K>B. arm64-ret density: <D> per KB. x86-ret bytes: <X>
> (<0.5%/KB). x86 oracle CGOs hash-match A2 baseline. Kernel probe:
> <digest>.

## Anti-cheat constraints

1. **Do not bypass `build-arm64/goalc/goalc`.** No hand-crafting
   arm64 CGOs from x86 ones, no `dd`-spliced bytes, no curl from
   a cache. The arm64 CGOs must come from a real `(mi)` run with the
   arm64 backend. The validator re-runs the script and diffs hashes.

2. **Do not let `out/jak1/iso/` end up with arm64 bytes.** That's the
   phase 25 cheat that broke the desktop oracle. After B1, `out/jak1/iso/`
   must contain exactly the x86 CGOs (hash-match `A2-baseline-x86-cgo-hashes.txt`)
   and `gk` must reach `link finish: logo`. The validator hashes
   both and runs gk.

3. **Do not lower the arm64-ret density threshold.** A real arm64
   function has at least one `ret` (4 bytes = 0xd65f03c0). A
   typical CGO of N functions has at least N rets. Average jak1
   function is ~150 bytes, so a 100KB CGO would have ~600
   functions and ~600 rets → density ≥ 6/KB. The validator demands
   ≥ 3/KB (half that, to allow for inlining). A pass with <3 rets/KB
   means the CGO is mostly data, not code — and that's a bug worth
   finding.

4. **Do not modify do_codegen or ObjectGenerator in this phase.**
   B1 verifies A2-A4's work; it does not extend it. Validator diffs
   `goalc/compiler/IR.cpp`, `goalc/emitter/IGenARM64.cpp`, and
   `goalc/emitter/ObjectGenerator.cpp` against A4's landing commit
   and fails on any non-trivial change.

5. **The `x86_ret_count` in arm64 CGOs SHOULD be low but won't be
   zero** — `0xc3` is one byte and shows up randomly inside arm64
   instruction streams. The validator tolerates up to 1% of total
   bytes as 0xc3-matches. A CGO with >1% 0xc3 is suspiciously
   x86-shaped.

## Pitfalls

- **Disk space**: `(mi)` produces ~15 MB of CGOs and ~20 MB of .o
  files in `out/jak1/obj/`. Running both backends consecutively
  doubles that briefly. Should be fine but worth knowing.

- **`build-arm64/goalc/goalc` rebuild may pick up shared changes from
  the build/ tree.** Cmake-cache propagation between two configured
  build dirs sometimes surprises. After the rebuild, verify the
  goalc binary has the new code by running `goalc --help` and
  confirming `--ir-emit-stats` is in the option list (added in A1)
  and the new fix-up kinds are referenced in ObjectGenerator.cpp.

- **x86 `(mi)` after the arm64 `(mi)`**: jak1's source files have
  no platform-specific code paths (GOAL is the same for both
  targets), so a clean x86 (mi) should produce the same bytes as
  the A2 baseline. If the hashes don't match, **something in shared
  code drifted** — A2's claude was careful to avoid this; B1 must
  not introduce drift either.

- **A4's kernel probe expects a specific symbol-table layout.** If
  jak1's source changed between A4 and B1 (it shouldn't have —
  A4 didn't edit any .gc files), the digest may differ. The
  validator only requires nonzero + reproducible, not equality to
  A4's value.

- **The script must be runnable from a fresh shell** — no
  reliance on env vars set elsewhere. The validator runs it in a
  clean subshell with just $PATH.

## Done definition

`.autoport/validators/phase-B1-cgo-regen-strict.sh` exits 0. Checks:

1. Arm64 CGOs exist at `out/jak1-arm64/iso/` (KERNEL/ENGINE/GAME).
2. Arm64 CGO sizes ≥ 50KB (KERNEL), 1MB (ENGINE), 1MB (GAME) — sanity
   minimums; the actual figures will be similar to x86 sizes.
3. arm64-ret density ≥ 3 per KB in each CGO.
4. x86-ret (0xc3) density ≤ 1% of bytes in each arm64 CGO.
5. x86 CGOs at `out/jak1/iso/` hash-match the A2 baseline file.
6. Desktop gk smoke test reaches `link finish: logo`.
7. `build_b1_arm64_cgos.sh` is idempotent — validator re-runs and
   compares arm64 hashes between two runs.
8. `goalc/compiler/IR.cpp` / `IGenARM64.cpp` / `ObjectGenerator.cpp`
   unchanged since A4's commit.
9. Classifier byte-identical since A1.
10. Kernel probe re-runs and produces the same digest twice.
