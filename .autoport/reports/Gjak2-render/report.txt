3. THE TRUE REMAINING BLOCKER (corrected, clean diagnosis)
------------------------------------------------------------------------
After the 5 fixes, the device boots jak2 through InitMachine -> IOP/overlord -> KERNEL.CGO
-> GAME.CGO link, then crashes during boot-link top-level exec (before any frame). With the
handler clean (5 runs): JAK1-ON-JAK2=0, BADPTR 0xc4001b10=0 (artifact gone). The real fault:
  - A `BLR Xn` where the branch target is a base-relative pointer `ADD Xn, Xn, X15`
    (X15 = g_ee_main_mem = 0x7f00000000, consistent — not ASLR).
  - The formed target is CORRUPT: 0xfe001b0c84 / 0xfe872d7664 (top byte 0x7f DOUBLED to
    0xfe = 2*base + offset), or 0x7f00000000 (bare base, offset dropped), or a stale ptr.
  - i.e. arm64 base-relative address formation doubles the EE base or drops the GOAL offset.
  - Crash object VARIES with ASLR/heap layout (display / decomp-h / vif-h / timer / smush-
    control-h; 55-258 objects) — data-dependent, single-threaded (goal-active=1), device-only
    (the fixed-layout qemu never triggers it -> reaches 420).
This is the jak1 A19-A42 "double-EE-base / offset-register (R15/X15) rebase" codegen class
(memory: arm64_x86_model_reg_ids, a35_state). The fix is in the goalc arm64 emitter/regalloc
(the ADD Xn,Xn,X15 rebase site) + a full arm64 CGO regen. jak1 fought this class across ~20
phases; the jak2 manifestation is a NEW pattern jak1's fixes did not fully cover.

FALSIFIED hypotheses (each tested with device/qemu evidence, don't re-chase): alloc-from-heap
garbage-type as the bug (was the a37/a11/handler artifacts); art-h segment stomp (was
ultimate_memcpy, fixed); cross-thread GOAL race (goal-active=1); a17 premature bind; jak1
symbol funcs on the boot path (0 hits — only the handler); method_set corrupt-Ptr<Type>
(tripwire 0 hits — crash is upstream of method_set); IOP/overlord DMA stomp (buffers are high-heap).
