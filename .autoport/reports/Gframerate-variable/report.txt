RESULT: VARIABLE FPS + CONSTANT SPEED

WHAT WAS WRONG (root cause, measured)
-------------------------------------
The engine scales all physics/animation/game-time by an INTEGER per-frame
time-ratio computed in display-frame-start (drawable.gc:978):
    time-ratio = floor(timer-count / *ticks-per-frame*) + 1   (snap <1.3 -> 1.0)
    seconds-per-frame = time-ratio / target-fps   (set-time-ratios, display.gc:56)
This is exact only when each frame's real duration is a clean integer multiple of
1/target-fps (a vsync-LOCKED panel — how the desktop stays correct at any refresh).
On the Redmi (eae4df44) TWO facts broke it:
  1. target-fps was hardcoded 60 while the device renders FREELY above 60 (~73 fps
     light) — the GL loop's SDL_GL_SetSwapInterval(1) reports "ok" but does NOT
     FIFO-block (mailbox/queue swap, dumpsys: active mode 60 Hz, peak 90). So at
     light load the game clock advanced 73/60 = ~1.22x too FAST.
  2. sub-60 loads land at FRACTIONAL budgets (47 fps = 1.28 budgets) the integer
     time-ratio cannot represent -> snaps to 1 (slow) or flips to 2 (fast) -> the
     owner's "un coup trop vite, un coup trop lent". The old LOCK forced a 30/60
     whole-vblank grid (capping fps + flapping ~50 at the boundary) to dodge this.


THE FIX (runtime/translation-layer only; engine goal_src untouched -> gold clean)
---------------------------------------------------------------------------------
1. Software-vsync cap on the EE game loop, in android_gfx::vsync() (the once-per-
   frame syncv barrier). The driver's SwapInterval(1) doesn't FIFO-block, so we
   EMULATE it: vsync() returns no more than target-fps times/sec (EINTR-robust
   re-sleep loop; the app's SIGILL crash-repair handler delivers signals).
   This is a MAX-rate cap only — under load fps drops FREELY (47, 30, 22...), it
   is NOT the removed 30/60 grid. android/android_gfx.cpp vsync() (~l.838).
   The old GL-thread present cap could not gate the EE loop (vsync()'s frame_idx
   barrier returns early when the EE outruns the GL chain pickup), so it lives in
   vsync() where the game clock itself is bounded.

2. Error-feedback game clock driven by REAL wall-clock dt, ONCE PER FRAME, in
   a35_read_ee_timer / a35_gfps_frame_tick (android/gk_android_main.cpp ~l.480).
   The frame signal is __send-gfx-dma-chain (drawable.gc:1231, exactly one call
   per rendered frame) — NOT the timer reads (which fire several times per frame
   at irregular gaps and double-counted). Each frame:
       desired += real_dt * target-fps ; k = round(desired - emitted) clamp[1,4]
       emitted += k ; advance the returned clock by the MIDDLE of time-ratio k's
       band so the engine's floor()+1(snap) formula resolves to exactly k.
   Long-run sum(k) == real_dt*target-fps -> game-time == real time at ANY fps,
   residual carried (bounded). a35_read_ee_timer now returns this virtual clock
   (the old 30/60 g_gspeed_clock_* publish + branch are DELETED; globals removed
   from android/android_gfx.{cpp,h}).

3. target-fps wired to the panel REFRESH (Android-gated) in reset-gfx
   (goal_src/jak1/pc/pckernel-h.gc:329): set-frame-rate! to
   pc-get-active-display-refresh-rate (guarded >0, else 60; x86 keeps 60 so the
   pristine x86 path is byte-identical). On the 60 Hz Redmi this resolves to 60.

4. IOP/cutscene vblank pacer unpinned from a hardcoded 60: iop_vblank_pacer_loop
   (android/android_gfx.cpp) now paces at Gfx::g_global_settings.target_fps live
   (the VBlank_Handler advances gFakeVAGClock by 1024/target_fps, so pacer_Hz ==
   target_fps keeps the cutscene/stream clock = real-time). 60 on the Redmi
   (unchanged cadence -> Gd1 cutscene real-time preserved), tracks refresh on
   non-60 panels.

KEPT: the anti-flicker hold-last-frame (8b330f996) in android_renderer.cpp
(present_this_cycle / never-present-undrawn / s_ever_drew) is intact.
