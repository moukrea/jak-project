======================================================================================
SUMMARY / ROOT CAUSE (named)
======================================================================================
The Rock Village -> Swamp crash-to-home is a null/garbage method dispatch at
process-drawable.gc:636  `(if (-> gp-0 effect) (effect-control-method-9 ...))`:
joint-control.effect (offset 0x28, type effect-control) holds a garbage GOAL pointer
instead of #f, so the #f-guard passes and a method is dispatched on an invalid
receiver -> SIGSEGV on the `(-> effect type)` -4 read.

This is NOT an emitter/codegen bug. goalc output is byte-correct on BOTH backends
(the `#f` store is `mov x9,x14; sub x9,x9,x15`, correct). The defect is a RUNTIME
ABI-mismatch in the mips2c GOAL<->C++ trampoline, i.e. exactly the "x14-clobber path"
this phase was queued for — and it is NOT the _arg_call/_stack_call boundary
(commit fd28435b6 already fixed those with x13/x14/x15 saves). It is the
ExecutionContext gpr-s7 SEED SEMANTICS in `_mips2c_call_arm64`:

  * arm64 live register x14 ("st") holds the HOST address of the symbol table
    (the _call_goal*_arm64 trampolines set `add x14, st, off`). x86 register r14
    holds the GOAL OFFSET of the symbol table (already offset-subtracted).
  * `_mips2c_call_arm64` seeded ExecutionContext gpr s7 (+368) with RAW x14 (host).
    x86 `_mips2c_call_systemv` seeds it with r14 (GOAL offset). DIVERGENCE.
  * Every mips2c body that calls back into GOAL via `ExecutionContext::jalr`
    (game/mips2c/mips2c_private.h:382) forwards gpr s7 as the `st` arg to
    `_call_goal8_asm_arm64`, which RECONSTRUCTS `x14 = st + off` (`add x14,x4,x5`,
    asm_funcs_arm64.s). A host-valued st RE-ADDS the EE base -> a torn x14 in the
    GOAL callee -> every `(set! (-> obj field) #f)` there stores garbage (x14-x15)
    instead of #f. `new joint-control` (joint.gc:498 `(set! (-> v0-0 effect) #f)`)
    is exactly such a store; when swamp actor construction runs inside a
    mips2c->jalr callback, joint-control.effect = garbage -> the crash.

NAMED BUG CLASS: arm64 "double-EE-base" torn register on the mips2c->GOAL callback
path (same class Gmatch band-aided at a different site via g_dblee_repairs). The
divergence is host-vs-GOAL-offset in the ExecutionContext gpr s7 seed.

x86 is untouched, so it never had this: x86 gpr s7 = r14 = GOAL offset, and
`_call_goal8_asm_systemv` sets `mov r14, st` (NO +off). arm64's `+off` reconstruction
is the asymmetry that makes a host-valued gpr s7 fatal.

FIX (file:line) — goalc UNCHANGED, engine goal_src UNTOUCHED, x86 asm UNTOUCHED
======================================================================================
game/kernel/asm_funcs_arm64.s , `_mips2c_call_arm64` , gpr s7 store (ExecutionContext +368):

  BEFORE:  str x14, [sp, #+368]          ;; gpr s7 = raw host address of symtab  (WRONG)
  AFTER:   sub x11, x14, x15             ;; st as GOAL offset (host_symtab - EE_base)
           str x11, [sp, #+368]          ;; gpr s7 = GOAL offset (x86-identical semantics)

x15 is the EE base / GOAL offset here (confirmed by the adjacent gpr-sp store
`sub x11,x11,x15 ;; GOAL-relative context address (x15 = GOAL offset)`).
x11 is free scratch at this point (its t3/arg7 value was already spilled at +176,
and the trampoline itself reuses x11 as scratch on the next line).

gpr s6 = pp (+352) is deliberately LEFT as raw x13 — CORRECT: `_call_goal8_asm_arm64`
passes pp through with `mov x13, x3` (NO +off), so pp round-trips identically on both
backends. Only st is reconstructed with +off, so only st must be seeded as a GOAL
offset. (The qemu A/B below confirms gpr s6 is raw on both variants.)
