             GLIDE= a big move spread over >2 samples with no single dominant jump

                    boots; we compare the ORDERED pattern (commands spread vs
                    collapsed; cut count; presence of a non-establishing glide).

## THE DEFECT ON arm64 (DEVICE BASELINE, no fix) — reproduced deterministically
   GCINE-SP shows the anim frame `af` (= ja-aframe-num) SPIKE at the misty-load
   part boundary while the raw stream clock stays smooth:
       ct=332480 strpos=41735 af=1223.20  part=10     <- normal
       ct=332720 strpos=42007 af=43179.0  part=10     <- SPIKE (af = strpos+1172)
       ...      (af stays ~43000-45000 for the whole misty stall) ...
   With af spiked, execute-commands-up-to(af) fires EVERY remaining joint command
   at once. GCINE-JC: all 18 commands (=9, captured x2) fire at ONE timestamp:
       JC cmds: 18   distinct ct: 1  [332505]         <- COLLAPSED
   So the camera jumps straight to the final "cameraB" joint and then that joint's
   animation GLIDES with no further switches:
       OC pos transitions: CUT=2  GLIDE=1
         GLIDE ct=345440..350480 len=29 cji 41->41 [SAME-joint]   <- the bug:
                                                  a 29-sample continuous pan
       cji seen: [4, 40, 41]    (never reaches the later plan, stuck on cameraB)
   => continuous pan where the original has discrete shot CUTs. THIS is the owner's
      defect, and it is arm64-only (x86 never spikes — see state-dump-x86.txt).

## ROOT CAUSE (arm64)
   During the misty-level load STALL the spool coroutine's FLOAT state is stomped
   on arm64 (a deep loader call clobbers the v8-15 callee-saved bank): the cached
   f30-0 AND the channel's frame-num / artist-step / artist-base all collapse to a
   ~1.0 scaling, so BOTH ja-aframe-num and strpos*f30-0 read ~the raw stream
   position (tens of thousands of frames). Every GOAL-readable anim value is
   corrupt; only the raw C++ stream position (current-str-pos) survives.

## THE FIX (goal_src/jak1/engine/load/loader.gc, ja-play-spooled-anim)
   Recover the spool-command frame from the raw stream clock when ja-aframe-num is
   implausibly large (anim tops out ~2570) AND has collapsed toward the strpos
   magnitude (af/strpos jumps from the normal ~0.03 to ~1.0): use strpos * f30
   with the immutable constant f30 = 0.05859375 * 0.5 (this cutscene's parts are
   all speed 0.5; the artist frame == strpos*f30 to <1 frame across the whole anim).
   On x86 ja-aframe-num is always the true small frame, so the branch is dead and
   host play is byte-identical.
