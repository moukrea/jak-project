Gbirds-anim — title-screen birds anim-advance dump (x86-first, NEVER pixels)
================================================================================
Owner ground truth: on the Jak1 title screen the birds over the tower RENDER but
are STATIC (no flight/bob/wing animation). This report proves, with deterministic
per-game-frame ANIM-ADVANCE dumps (no screenshots), that the device birds were
genuinely frozen (a real arm64 translation bug, NOT a stale-deployment artifact),
identifies the defect, fixes it in the translation layer, and re-measures the
device birds advancing 1-to-1 with the original.

RESULT: BIRDS ANIMATE MATCHING ORIGINAL (device, 1-to-1 source)

--------------------------------------------------------------------------------
WHAT THE "BIRDS" ARE (so the metric reflects the actual defect)
--------------------------------------------------------------------------------
The title flyover renders village1 (Sandover) behind the logo. The birds over the
sage-hut tower are the sparticle group `group-village1-sagehut-seagulls` (defpart-
group id 132, goal_src/jak1/levels/village1/village1-part.gc:699). They are NOT a
skeletal `ja`-animated process; their flight "animation" is driven by the per-frame
sparticle :func callback `bird-bob-func` (village1-part.gc:754, defpart 415):

    (set! (-> arg2 y)
      (+ (-> proc root trans y)
         (* -2048.0 (sin (* 218.45334 (the float (mod (current-time) 300)))))))

So the bird's vertical bob is a deterministic function of `current-time`
(= (-> *display* base-frame-counter), the per-game-frame anim clock). If the
callback runs each frame with an advancing current-time, the bob-y oscillates and
the bird flies; if the callback never dispatches (or the clock is frozen), the bird
is static. THE ANIM-ADVANCE METRIC dumped here is: per game frame, the bird's
current-time and the bob-y value bird-bob-func writes (for one latched bird,
ci=0x1a0130). Oscillating bob-y across frames == ANIMATING; constant/no-dispatch ==
STUCK.

Instrumentation (TEMPORARY, since REMOVED): identical C++ in the mips2c
sp-process-block-2d :func dispatch site (game/mips2c/jak1_functions/sparticle.cpp)
logging `GBIRDS2D ci=.. current-time=.. dt=.. bob-y=.. freeze=..`. Same C++ runs on
x86 (stdout) and the device (logcat, GK_STDOUT) — a true 3-way comparison from ONE
source. All temp instrumentation has been removed; only the permanent arm64 fix
remains (see FIX).

================================================================================
3) device  (eae4df44, arm64)  — BEFORE the fix  (calibrated, reproduced)
================================================================================
Build: fresh consolidated HEAD libgk (deploy_verify PASS) WITHOUT the arm64 2D
#f-guard. Same C++ instrumentation as x86, provably present in the deployed libgk
(verified via `strings`), printf routing confirmed working (other GK_STDOUT
diagnostics appear).

BEFORE result (file device-before-gbirds.txt): GBIRDS2D lines = 0. ZERO bird
dispatches across the whole title flyover (boot reached logo; 0 crashes; app
foreground). i.e. bird-bob-func NEVER runs on arm64 => the bird bob-y is never
updated => delta = 0 across every frame => the bird is FROZEN/STUCK. This is the
owner's reported "static birds", reproduced deterministically (0 vs x86's 5168).
This is the calibrated BEFORE (device anim-frame stuck, advance Δ≈0).

Root cause (localized x86-first, then confirmed on device): in the mips2c
`sp-process-block-2d` block_1 (sparticle.cpp), the two `beq reg, s7` #f-checks
(`(-> cpuinfo valid)` at +128, and the `(paused?)` arg `s2`) used the full-64
`sgpr64` compare and LACKED the arm64 low-32 `gpr_addr` guard that the sibling
`sp-process-block-3d` block_1 already had. On arm64 a GOAL pointer loaded via
sign-extended `lw` arrives as the bare low-32 offset while gpr s7 is the full host
symbol base (0x7f...), so a full-64 compare MISSES #f. The `s2`(paused?)==#f branch
that routes a LIVE 2D particle to block_8 (the func-dispatch path) was therefore
never taken on arm64 — the bird fell through to the skip path and block_13's
bird-bob-func jalr was never reached. The 2D block was simply never given the fix
the 3D block received. x86 is unaffected (operands consistent there), which is why
x86 dispatched 5168x while the device dispatched 0x.

================================================================================
FIX (translation layer only — NOT goal_src)
================================================================================
game/mips2c/jak1_functions/sparticle.cpp, sp_process_block_2d block_1: add the
`#if defined(__aarch64__)` low-32 `gpr_addr` guard to BOTH `beq v1,s7` (valid) and
`beq s2,s7` (paused?) #f-checks, mirroring sp_process_block_3d block_1 verbatim.
arm64-gated; x86 path unchanged (#else keeps sgpr64). No goal_src change; gold
pristine. Same bug class as the documented arm64 mips2c #f-guard family
(Gd2/Gsprite/Gnewgame).
