0. TL;DR
--------------------------------------------------------------------------------
The camera GAME-STATE is smooth and already rides the SAME fractional
time-adjust-ratio Jak uses (the prime-lead "camera rides the flickery INTEGER
time-ratio while Jak rides the fractional one" is FALSIFIED by device + code
evidence). The pan judder is a PRESENT-CADENCE problem: the Android EE-loop frame
cap paced with a coarse sleep_for() (no busy-spin), so on this device the ~1-2ms
sleep-wakeup jitter (which also OVERSHOOTS) made the on-screen present intervals
UNEVEN, and the overshoot nudged ~11-19% of frames into a k=2 DOUBLE game-time
step ("jumps") — even when the fps was "fine" (~60). Because the GL present is
1:1-slaved to the EE-loop cadence (state-anchored: present dt == EE dt every
frame), that jitter reads as camera-pan judder (full-screen motion), while Jak's
slow local motion hides it. FIX (android runtime glue only): the frame cap now
mirrors the smooth desktop FrameLimiter — sleep to a ~1.5ms margin then BUSY-SPIN
to the exact deadline. State-anchored device-vs-golden before->after at a held
~60fps (owner's dynamic-render-scale-60 "fps fine" case): present-dt jitter sd
4.55->1.62ms, frames-off-cadence 64.5%->5.6%, k=2 "jumps" 19.2%->1.7% (pan). Game
speed unchanged (59.99 game-units / real-second). No fps quantization, no 30/60
lock, engine goal_src untouched, golden pristine, x86 "link finish: logo".

--------------------------------------------------------------------------------
2. WHY, EXACTLY (the named timing cause)
--------------------------------------------------------------------------------
The EE-loop frame cap (android_gfx.cpp vsync()) paced to an absolute deadline
s_next with:  while (now < s_next) { sleep_for(s_next - now); now = now(); }
On Android sleep_for's wakeup granularity is ~1-2ms AND it tends to OVERSHOOT.
Consequences, measured at a HELD ~60fps (dynamic render scale ON, target 60 — the
owner's "fps fine" play condition, where the cap engages with headroom, k mostly 1):
  (a) UNEVEN presents: each frame lands 1-2ms off the 16.67ms grid -> present dt
      sd 2.85ms at rest, 30% of frames >2ms off; WORSE while panning (sd 4.55ms,
      64.5% >2ms). Constant-delta camera shown at uneven intervals = pan judder.
  (b) k=2 "JUMPS": the sleep OVERSHOOT pushed the mean frame to ~18.5ms (~54fps,
      not 60) and nudged real_dt over the k=1 band often enough that ~11% (rest) /
      ~19% (pan) of frames took a k=2 DOUBLE game-time step. Each such frame
      advances the camera by 2x -> a visible micro-jump during a pan. (k = the
      engine integer time-ratio, drawable.gc:978 / set-time-ratios display.gc.)
Both are the owner's "jittery / jumps" — and both occur "even when the fps is
fine" because they are cap-precision artifacts, not fps drops.

--------------------------------------------------------------------------------
3. THE FIX (android runtime glue only; engine goal_src + gold untouched)
--------------------------------------------------------------------------------
android/android_gfx.cpp vsync() software frame cap: replace the coarse
sleep_for()-the-whole-remaining-time loop with the SAME technique the smooth
desktop build uses (common/util/FrameLimiter.cpp): coarse-sleep to a ~1.5ms margin,
then BUSY-SPIN the final sliver to the exact absolute deadline s_next. EINTR-robust
(the spin reaches the deadline even if the SIGILL crash-repair handler cuts a sleep
short). This is golden-faithful: the desktop is smooth precisely because its
FrameLimiter sleeps-to-margin-then-spins; Android now does the same.

Properties preserved:
  * MAX-rate cap ONLY — NOT a forced 30/60 grid, NO fps quantization. Under load
    the fps still drops FREELY (the cap simply doesn't engage when render > budget).
  * Game clock STILL driven by REAL dt (a35_read_ee_timer error feedback, byte
    UNCHANGED) -> constant real-time speed. A clean 60fps/k=1 advances game-time at
    the SAME real rate the old jittery ~54fps/k-dither did (the error feedback holds
    it). Measured after the fix: 59.99 game-units / real-second (baseline 59.98,
    pan 60.01) -> speed constant, the speed bug is NOT reintroduced, no 30/60 lock.
  * Boot path untouched (only the post-renderer-ready cap block changed).

Files: android/android_gfx.cpp (the fix). Diagnostic probes (kept, gated):
android/gk_android_main.cpp, android/android_renderer.cpp,
game/graphics/pipelines/opengl.cpp. NO goal_src changed. .autoport/gold untouched.

--------------------------------------------------------------------------------
5. HONEST RESIDUAL / SCOPE
--------------------------------------------------------------------------------
* The AFTER present-dt sd is ~1.6ms (much improved from 4.55), NOT sub-millisecond,
  and occasional heavy frames still spike to 32-36ms. The busy-spin removes the
  SLEEP-wakeup jitter, but it can only pace frames that finish UNDER the vblank
  budget; when the Adreno 618 is genuinely render-bound (render > budget) the cap
  cannot engage and the residual is real render-time variance. On this device the
  cure for that is dynamic render scale holding the target (the owner's setup) so
  the cap keeps engaging — which is exactly the condition measured here.
* True free-fluctuating-fps-AND-smooth at a render-bound fractional fps is
  fundamentally limited by the PS2 integer-time-ratio engine displaying at uneven
  intervals; the only ways to make it perfectly uniform are (i) present=k/60
  pacing, which re-quantizes fps to 60/30/20 and can flap at marginal loads (the
  behavior the owner rejected), or (ii) render-time camera-view INTERPOLATION (an
  engine/renderer change, and infeasible to interpolate to a HIGHER rate on a
  GPU that can't render faster). Neither was done; both are noted for the owner.
  The shipped fix is the golden-faithful, zero-risk win that addresses the owner's
  stated "even when the fps is fine" case without any of those tradeoffs.
