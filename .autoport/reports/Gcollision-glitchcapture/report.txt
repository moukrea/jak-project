1. WHAT WAS BUILT + DEPLOYED (the capture build) — DONE, VERIFIED ON DEVICE eae4df44
================================================================================================
An ALWAYS-ON, glitch-triggered collision-math dump, entirely C++-side in libgk (NO CGO rebuild;
the GOAL game logic the owner plays is byte-identical). game/kernel/jak1/kmachine.cpp:
  - collision_glitch_capture_tick(), called once per game-logic frame from pc_set_levels (GOAL
    __pc-set-levels, level.gc:1370), on the EE/kernel thread post engine-update.
  - Each frame it reads Jak's persistent collide-shape-moving fields from EE memory (root =
    *target*+108; offsets = GOAL deftype :offset-assert - 4, identical x86/arm64 so the dump is
    byte-comparable): trans, quat, transv, rotv, status, prev-status, local/surface/poly/
    ground-poly normals, ground-touch-point, gravity-normal (via dynam basic ptr +28), and the
    dot-product angles (surface/poly/touch) + coverage + ground-impact-vel.
  - Ring buffer of 9 frames (8 pre-glitch + the trigger frame) so the ONSET is captured.
  - Glitch SIGNATURES (tunable via android props cc_jump / cc_vel / cc_normeps; cc_disable):
      NONFINITE     — any NaN/Inf in trans/transv/normals/angles (bypasses cooldown)
      DEGEN_NORMAL  — a collision normal is non-unit (|len-1|>eps) = divergent normalize/length
      TRANS_JUMP    — one-frame trans teleport > 20 m (clip / under-map)
      TRANSV_SPIKE  — transv magnitude > 50 m/s (eject / projection)
  - On trigger: append the ring buffer (hex8 floats, exact bits) to
    /data/data/<pkg>/files/collision_glitch.txt, flush+fsync per hit; capped at 400 dumps; and
    print a live "[CC] GLITCH #n ..." line to the GK_STDOUT logcat tag for the supervisor.
  - Gated: ON by default on Android (capture build); on x86 only if OG_COLLISION_CAPTURE is set,
    so the validator's x86 smoke stays clean.

KEY METHODOLOGY FINDING (rules a class out, points to the next step):
  The collision REACTION ops are bit-identical x86/arm64. Confirmed two ways:
    (a) source audit: goalc's arm64 backend emits NO fused multiply-add — .add.mul.*.vf lowers to
        separate FMUL+FADD, .sqrt.vf is full-precision FSQRT, scalar +/* are FADD/FMUL
        (IGenARM64.cpp / IR.cpp). The "FMA in vector-length" hypothesis is FALSIFIED at the source.
    (b) empirical: the oracle's x86-vs-arm64 diff on real device operands is IDENTICAL.
  => the owner's finite-but-wrong collision divergence originates UPSTREAM, in collision DETECTION
     (the broad/narrow phase that computes the normals/intersect that FEED the reaction), not in
     the reaction layer that this capture reconstructs. The reaction capture LOCALIZES the glitch
     frame + CLASSIFIES it (non-finite? non-unit normal? finite-but-wrong direction?); if the
     owner dump shows finite unit normals with a wrong transv, the next step is a targeted
     DETECTION-stage capture (the collide leaf is mips2c = C++, instrumentable without a CGO
     rebuild) fed to the x86 oracle. fmin/fmax (Gcollision-nanroot) is KEPT (real conversion fix).
