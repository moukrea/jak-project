Gcollision-glitchcapture — name + fix the REAL arm64-vs-x86 collision divergence at degenerate contacts
======================================================================================================

RESULT: REAL GLITCH COLLISION DIVERGENCE NAMED + FIXED
  The owner's in-game collision glitch (Jak clips / ejects / under-maps at degenerate/grazing
  contacts) is the goalc arm64 codegen emitting the WRONG condition codes for FLOAT `<` and `<=`
  comparisons: on an unordered (NaN) operand arm64 returned #f where x86 returns #t. At a degenerate
  contact a zero-length vector-normalize! makes a NaN `coverage`, and `(< coverage 0.0)` /
  `(< coverage 0.9999)` (collide-reaction-target.gc:141/145) then take the WRONG branch on arm64 —
  skipping the coverage-recovery / low-coverage surface handling — yielding a finite-but-WRONG
  push-out (the clip/eject/under-map). NAMED via the x86 oracle on the real degenerate-contact NaN
  operand; FIXED in the translation layer (goalc/compiler/IR.cpp, arm64 float LT->LT, LEQ->LE);
  AFTER the fix arm64 == x86 on the captured operands. The OWNER play-test on the fixed build is the
  final gate.

WHY THE PRIOR FIXES DID NOT FIX IT (and why this is the real root)
  - fmin/fmax (Gcollision-nanroot): op-proven (576 synthetic pairs) but a DIFFERENT op. The
    collision push-out NaN flows through `<`/`<=` COMPARISONS, not min/max — there is no fmin/fmax
    on that path (collide-reaction-target.gc:139-145). So the min/max fix could never sanitize it.
  - The collision MATH is bit-identical arm64-vs-x86 (detection + reaction leaves, vector-normalize!,
    dot, length — all IEEE FADD/FSUB/FMUL/FDIV/FSQRT; no rsqrt estimate, no FMA, no integer divide;
    FTZ off on both; no mips2c allowlist asymmetry). The NaN itself is produced IDENTICALLY on both
    backends. The divergence is NOT in the arithmetic — it is in how a CONDITIONAL BRANCH consumes
    that NaN. That is why every prior "divergent collision op" hunt came up identical, and why the
    post-frame reaction-output capture saw finite values (the NaN is a consumed intermediate; the
    wrong branch yields a finite-but-wrong push-out that the post-frame *target* read shows as finite).

2. THE x86 ORACLE ON THE DUMPED OPERANDS — NAMES THE FIRST DIVERGENT OP
======================================================================================================
cmp_oracle.cpp runs the EXACT goalc-emitted comparison instructions on BOTH backends on the captured
operand set (the real 0.0/0.0 NaN the collision normalize produces, plus Inf/±0/finite), on the REAL
device (eae4df44) and the x86 host. x86 = `ucomiss a,b` + the goalc unsigned jcc; arm64 = `fcmp a,b`
+ the goalc b.cond. Results (cmp_x86.txt vs cmp_arm.txt, summary cmp_oracle_summary.txt):

  FIRST DIVERGENT OP = the arm64 FLOAT `<` (LT) comparison, then `<=` (LEQ):
    BEFORE: 84 of 726 rows diverge (arm64 != x86) — every one with a NaN operand:
            LT 21, LEQ 21, EQ 21, NE 21.
    The collision case:  x86 (< NaN 0.0) = 1 (#t)   <- correct: enters coverage-recovery branch
                         arm64 (< NaN 0.0) = 0 (#f)  <- WRONG: skips it -> wrong push-out (clip/under-map)
    Root: x86 uses `ucomiss`+`jb`/`jbe` (CF=1 on unordered -> `<`/`<=` TRUE on NaN); goalc arm64 used
    `fcmp`+`b.MI`/`b.LS` (N/C tests -> FALSE on unordered). The two backends disagree on EVERY NaN
    `<`/`<=`. (Inverted `>=`/`>` route through LT/LEQ, so this is also the documented "(>= c NaN)
    wrongly #t" / Gtitle bug.)

======================================================================================================
3. THE FIX (translation layer; goal_src 1-to-1; x86 untouched)
======================================================================================================
goalc/compiler/IR.cpp, IR_ConditionalBranch::do_codegen_arm64 — for FLOAT conditions only:
    LT  : ARM_COND_MI  ->  ARM_COND_LT   (N!=V: a<b OR unordered == x86 jb)
    LEQ : ARM_COND_LS  ->  ARM_COND_LE   (Z|N!=V: a<=b OR unordered == x86 jbe)
  GT/GEQ already matched x86 (GT/GE read N,V so unordered is false == x86 ja/jae) — unchanged.
  do_codegen_x86 is byte-untouched. No goal_src change (the bug is purely in arm64 codegen; the GOAL
  source and the x86 build are the 1-to-1 reference). Single codegen site — the boolean-value form
  (compile_condition_as_bool) reuses IR_ConditionalBranch, so the branch and value forms are both fixed.

  AFTER the fix (arm_fix column, same device run): arm64 == x86 on ALL LT/LEQ rows (42/42 fixed),
  including the collision `(< NaN 0.0)` -> #t == x86. Zero regression on finite/Inf/±0 operands (only
  the unordered/NaN result changed; ordered results were already identical). 42 EQ/NE-with-NaN rows
  remain divergent (a separate x86 ZF NaN-as-equal quirk) — NOT on the collision path, documented and
  intentionally out of scope (see cmp_oracle_summary.txt / fix-summary).
