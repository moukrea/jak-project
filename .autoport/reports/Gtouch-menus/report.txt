Phase Gtouch-menus — make the in-game menus fully TOUCH-browsable (no D-pad)
=============================================================================
RESULT: MENUS TOUCH-BROWSABLE
Owner mandate (2026-07-02): on Android the option/progress menus must be fully
navigable by TAP — tap a menu entry to enter its submenu / reveal sub-options,
tap a sub-option to select it, tap Back / outside to go back — all by touch,
WITHOUT needing the D-pad. D-pad + gamepad keep working (touch is additive).
Device eae4df44 only. Verified with REAL `adb -s eae4df44 shell input tap X Y`.

--------------------------------------------------------------------------------
TAP -> ACTION MAPPING (how a tap reproduces the D-pad/confirm interaction)
--------------------------------------------------------------------------------
A tap on a menu ROW focuses it (sets option-index) and then reproduces EXACTLY
the D-pad+confirm interaction a controller user would perform for that row's
type, by replaying a short synthetic press sequence over consecutive frames
(so all the existing enter / toggle / cycle / commit logic is reused verbatim):

  * menu / button / action row  -> CONFIRM               (enter the submenu / activate)
  * on-off / carousel / slider / aspect / language  ->  CONFIRM, then a LEFT or
        RIGHT (chosen by which HALF of the row was tapped), then CONFIRM to commit
        -> a single tap CHANGES the value / cycles the carousel option. Tapping the
        LEFT area selects one way, the RIGHT area the other (carousel left/right).
  * yes-no row -> a direct LEFT/RIGHT (this type reacts without edit-mode)
  * a tap OUTSIDE the row list (below/above the rows) -> BACK
  * the visible "Back" row -> CONFIRM on it -> BACK

Touch is purely additive: the flags a tap raises are OR-ed into the SAME input
guards the D-pad uses in respond-common (cpad-pressed? up/down/left/right/x/
circle/square/triangle), so the D-pad and a Bluetooth gamepad keep working
unchanged. Engine goal_src is UNTOUCHED — all logic lives in
goal_src/jak1/pc/progress-pc.gc (pc/ only) plus the Android touch glue.

--------------------------------------------------------------------------------
HIT-TESTING (map touch x,y -> the on-screen menu row rectangle)
--------------------------------------------------------------------------------
The menu already computes each row's on-screen font ORIGIN while drawing it, so
we reuse that layout. Data flow:

  Android overlay (TouchOverlayView.onPointerDown) — when a finger DOWN misses
    every on-screen control AND NativeGk.isInMenu() is true — forwards the
    NORMALIZED tap (x/viewWidth, y/viewHeight) via NativeGk.onMenuTap(nx,ny).
  JNI (gk_android_main.cpp) stores nx,ny (scaled to [0,10000]) + a monotonic
    tap-sequence counter in atomics.
  pc-get-touch-tap (new pc-* bridge; live impl a35_pc_get_touch_tap on Android,
    no-op flag=0 stub pc_get_touch_tap on desktop so x86 stays safe) hands GOAL
    the tap x,y + a "fresh" flag (1 exactly once per new tap).
  draw-options (progress-pc.gc) republishes every visible row's NORMALIZED
    on-screen rect each frame via menu-touch-record! (menu-touch-row: cx, cy,
    half-h + abs-index) — using the row's actual font origin position.
  respond-common calls menu-touch-drive!: on a fresh tap it hit-tests the tap
    (fx,fy) to the NEAREST row by vertical center within the row band, sets
    option-index to that row, and builds the synthetic press sequence.

Virtual->screen transform (CONFIRMED ON-DEVICE eae4df44): a row's normalized
screen center maps LINEARLY from its font origin:  cy = 0.00478*oy ;  cx ~ 0.50
(rows drawn with a horizontal-center flag). Calibrated from the title menu rows
(oy = 40..165 step 25 -> screen fractions 0.19..0.79 step ~0.12). This is
framebuffer-independent (Java sends normalized coords), so no window size is
needed GOAL-side. Nearest-row matching tolerates small transform error.
