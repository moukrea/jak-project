RESULT: PERF CLEAN 32->37 FPS   (night Rock Village fire zone, render-bound;
                                  render_ms 28.4->25.8 ms = +9%; per-feature below)

The v5 build shipped ALL Gperf-particles optimizations ON and CORRUPTED the image in
real play (geometry pops in/out; textures flicker day/night/sunrise). The supervisor
STOPGAP defaulted them all OFF (v4 renderer restored). This phase re-earns each
optimization CORRECTLY: it KEEPS the 5 that are provably image-identical to the v4
renderer AND a real gain, and DROPS the 3 that corrupt the image or give no real gain.
Ship set = sprite-lean + state-cache + sprite-instance + shrub-static-idx + 2d-NEON.

--------------------------------------------------------------------------------
0. WHY THE v5 VALIDATION WAS BLIND, AND WHAT THIS REDO FIXES
--------------------------------------------------------------------------------
The v5 "0-flicker" proof was pose-HELD (camera static -> geometry pop invisible) with
the clock PINNED to night (-> TOD cycling hidden). This REDO validates under REAL,
MOVING gameplay with the time-of-day advancing NATURALLY, plus a rigorous pixel-parity
proof, plus a detector proven to fire on injected defects. Two confounds that would
have re-hidden the bug were found and eliminated first:
  (a) DYNAMIC RESOLUTION: the game's dyn-rs auto-scaler (pckernel-common.gc) changes
      internal render resolution every ~0.5-1 s based on fps. A mid-clip scale change
      is a global transient that the pop detector flags as "pop", and each boot took a
      different scale trajectory -> cross-config comparison meaningless. FIX: pinned the
      device pc-setting `dynamic-render-scale? #f` (fixed 100% internal res) for every
      capture, so the ONLY variable across configs is the perf feature under test.
  (b) FIRE-PARTICLE ANIMATION: the fire flame animates continuously and its frame-to-
      frame magnitude is variable; a naive clean-vs-clean "noise floor" under-samples it
      and can fake a "DIFFERS". FIX: the parity floor now includes a SAME-config v4-vs-v4
      pair (captures the fire variance symmetrically).

3. KNOWN-BAD CONTROL — proving the inspection ACTUALLY DETECTS pop + flicker
--------------------------------------------------------------------------------
The exact step the v5 validation skipped. Two layers:

(a) On-device re-enabled controls (the owner's v5 symptoms):
    pop-control = GOAL/GL overlap ON; flicker-control = TOD ping-pong ON. On THIS device
    neither produced a signal above the v4/clean band (overlap POP 48 <= v4 84; ping-pong
    saw 0.857 <= clean 1.314). This is an honest, important finding: the owner's pop
    (a live-EE-read race) and flicker (Adreno async-upload behavior) are DEVICE-SPECIFIC —
    the Redmi's Adreno 618 does not reproduce them at a magnitude the detector or the eye
    catches; the owner's much newer GPU does. (Same class as the Snapdragon-only swamp
    crash.) So the on-device control cannot, by itself, prove the detector works here.

(b) Synthetic injected defects — proves the detector (check works) is NOT worthless:
    inject into a real clean recording (tools/synthetic):
      - POP: a single-frame black hole (central rectangle blanked for ONE frame) every 20
        frames = "geometry vanished then returned".
      - FLICKER: an alternating +/-12% global luma sawtooth = TOD palette oscillation.
      result:                        POP events   frames_with_pop   FLICKER flip_rate / saw%
        ORIGINAL (no defect)         0            0                 0.000 / 5.06
        POP-injected                 320          20 (== injected)  0.55  / 6.97
        FLICKER-injected             1744         390               1.00  / 36.13
    The detector fires UNMISTAKABLY on both, catching exactly the 20 injected pop frames
    and driving flip_rate 0->1.0 on the sawtooth. Therefore "clean shows no pop/flicker"
    is a MEANINGFUL negative: when a real defect of that severity exists, detect.py flags
    it; the clean build has none.

4. PER-FEATURE VERDICT — re-earned ONE AT A TIME (kept / dropped + WHY)
--------------------------------------------------------------------------------
KEPT (image-invariant vs v4 by static analysis AND parity AND moving video; each a live
kill switch =1 restores the exact v4 path):
  * sprite-lean       — sprite-bucket allocation lifecycle only (keep map+ids capacity,
                        ids.clear() vs buckets.clear()); identical vertices/draws/order.
  * state-cache       — caches per-draw GL state keyed on (draw-mode, bound-tex), a pure
                        function; re-issued on every mode/tex change; invalidated on any
                        out-of-band state change. No skipped state that matters.
  * sprite-instance   — jak1-only; the instanced vertex shader differs from the corner
                        shader by ONE line (vert_id = {0,1,3,2}[gl_VertexID], the same
                        order the CPU path bakes). Byte-identical image.
  * shrub-static-idx  — caches Shrub's level-static single-draw index list (built with no
                        vis input); per-frame proto-vis still applied at draw time. Static.
  * 2d-NEON           — sparticle 2d aging inner loop as inlined float math, bit-identical
                        two-rounding to the scalar VU0 ops. GUARDED by -ffp-contract=off,
                        now added to sparticle.cpp in BOTH game/CMakeLists.txt and
                        android/CMakeLists.txt (it was previously passing only "by luck").

DROPPED (default OFF; opt-in '2' ONLY reproduces the known-bad control):
  * GOAL/GL overlap   — a GENUINE race: the renderer dereferences LIVE ee-memory that the
                        released GOAL thread overwrites — texture-upload source pixels
                        (TextureUploadHandler upload.page, TextureAnimator upload->data)
                        and the merc bone-matrix + mod/frag vertex data (Merc2), none of
                        which the dma_copier snapshots (upstream code itself documents
                        these as race-prone / "obvious holes"). This is the owner's
                        geometry POP. It is safe-ABLE — the unsafe reads are a bounded set
                        (texture-upload src + merc bones + merc mod/frag) that could be
                        snapshotted on the game thread — but that is a substantial, per-
                        renderer address-resolution change that CANNOT be correctness-
                        validated on the Redmi (device-non-repro), so shipping it here
                        would risk exactly another unverifiable false-green. STAYS OFF;
                        the snapshot fix is a dedicated follow-up. Correctness beats the fps.
  * TOD ping-pong     — samples the previous ping-pong buffer under a moving clock =>
                        day/night palette FLICKER (owner v5 symptom, device-specific
                        Adreno async-upload). No correct invalidation within scope. OFF.
  * TOD skip/memoize  — byte-identical when it fires, but the skip key (camera itimes)
                        CHANGES every frame under a moving clock, so it ~never fires =>
                        ZERO real-gameplay gain. Dropped as pointless under natural TOD.

5. NUMERIC GAIN of the kept set (in-boot A/B, night fire zone, resolution pinned)
--------------------------------------------------------------------------------
This scene is render-bound (render_ms 25-28 ms > 16.6 ms) so fps is NOT vsync-capped and
is directly measurable from the frame cadence. v4 (all kept OFF) vs CLEAN (all ON):
  metric                 v4         clean      delta
  frame-cadence fps      32.3       37.0       +4.7 fps (+14.6%)
  render_ms (median)     28.38      25.83      -2.55 ms (+9.0%)
  glbuild  (ms/60f)      43.03      22.70      -20.3
  glflush  (ms/60f)      51.86      42.38      -9.5
  GOAL spart2d (ms/60f)  41.03      28.90      -12.1
Per-feature attribution (toggle one OFF from clean; +delta = that feature IS a gain):
  * sprite-instance  -> the DOMINANT GL win: removing it raises glbuild 22.7->43.9 (+21.2)
                        and glflush +17.2. Accounts for essentially the whole glbuild gain.
  * 2d-NEON          -> the GOAL-thread win: removing it raises spart2d CPU 28.9->40.1
                        (+11.2 ms) — this is exactly the owner's CPU/submission bottleneck
                        in particle-heavy fire zones, so it is the most relevant gain for
                        the owner's device.
  * state-cache / sprite-lean / shrub-static-idx -> small in isolation at a static pose
                        (<=0.5 ms each) but image-invariant and additive; kept (free).
fps is vsync-capped ~60 in lighter/moving scenes; the gain there is the same CPU/
submission headroom (glbuild/glflush/spart CPU), which is what protects fps on the owner's
heavier scenes and device.
