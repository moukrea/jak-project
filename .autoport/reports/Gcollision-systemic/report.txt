Gcollision-systemic — pervasive arm64 collision divergence fixed at the ROOT
============================================================================

RESULT: ARM COLLISION MATCHES X86 (SYSTEMIC)

The owner reported collision broken EVERYWHERE on arm64 (x86 fine): clip through
walls, jumps under the map, eject far OR stuck-crouch near objects, invisible
walls / must-jump on visibly flat ground, blue-eco zone ejects off the cliff.
The owner's read ("related to the ARM conversion") is correct. This was NOT
another per-site bug: it is a SYSTEMIC, PERVASIVE arm64 float<->int conversion
divergence in the collision pipeline, fixed at the ROOT (the goalc AArch64
codegen of float->int), not by another symptom patch.


1. THE SYSTEMIC ROOT (named codegen op)
---------------------------------------
The arm64 goalc backend emitted a BARE `FCVTZS` for every GOAL float->int:
  - scalar  IR_FloatToInt  -> IGenARM64 float_to_int32  -> `fcvtzs Wd, Sn`
  - vector  IR_VFMath2Asm (.ftoi.vf) -> IGenARM64 ftoi_vf -> `fcvtzs Vd.4s, Vn.4s`
FCVTZS saturates float->int DIFFERENTLY from the x86 oracle (cvttss2si /
cvttps2dq) the GOAL collision code was decompiled and validated against:

        input            x86 cvttss2si/cvttps2dq    arm64 FCVTZS (bare)
   in s32 range          truncate toward zero        truncate toward zero  (same)
   -ovf / -Inf           0x80000000 (INT_MIN)        0x80000000            (same)
   +ovf / +Inf           0x80000000                  0x7fffffff (INT_MAX)  DIVERGES
   NaN                   0x80000000                  0                     DIVERGES

This is the SAME conversion bug class the per-site Gledge fix patched in ONE
mips2c op (vftoi0). The root is the conversion/codegen op being wrong PERVASIVELY:
the goalc-compiled GOAL collision code (collide-cache/collide-mesh/
collide-edge-grab, in the GAME+ENGINE CGOs) uses 58 vector `.ftoi.vf`
conversions to quantize triangle/query coordinates into the collision spatial
hash and AABB grid. Collision legitimately produces NaN/overflow coordinates in
degenerate/grazing/far geometry; x86 sends those to 0x80000000 (an out-of-bounds
cell that collision rejects), while arm64 sent NaN->0 / +ovf->INT_MAX (a valid
-looking cell), so arm64 selected a DIFFERENT collision triangle than x86 ->
wrong/absent push-out and a blown-up velocity integrator -> clip-through, eject,
invisible wall, under-map, stuck. One wrong conversion mode corrupted collision
broadly, exactly as the owner described ("everywhere").

Disassembly of the arm64 CGOs confirmed the root is IN the collision code:
collide-cache 51, collide-mesh 4, collide-edge-grab 3 vector `fcvtzs .4s` sites
(58 total), byte-for-byte matched 1:1 by x86 `cvttps2dq` at the same sites.


2. UNIT-DIFF SWEEP (x86 vs arm64, many -> 0) — the Gcollision-arm model
-----------------------------------------------------------------------
A) Conversion sweep (conv_sweep.cpp), cross-compiled x86 (GCC, the oracle) and
   arm64 (NDK clang, the device), over 75000 collision-realistic float inputs
   (positions, squared distances, near-div-by-zero, +/-Inf, NaN), run on
   device eae4df44:
     BEFORE (baseline: x86 oracle vs arm64 bare FCVTZS):  38285 / 75000  divergent
     AFTER  (x86 oracle vs arm64 cvttss2si-emulation):        0 / 75000  divergent
   Class breakdown of the 38285 BEFORE divergences: +ovf 21639, NaN 1110,
   Inf 612, in-range (rng) 0 (in-range conversions NEVER diverge, as predicted).

B) On-device sequence validation (seq_validate.cpp, eae4df44): the EXACT
   instruction words the goalc fix emits, run over 200000 inputs:
     SCALAR sequence vs x86 cvttss2si:   0 mismatches      (== x86)
     VECTOR sequence vs x86 cvttps2dq:   0 / 800000 lanes  (== x86)
     SCALAR sequence vs bare FCVTZS:     77873 differ      (proves it changes behavior)
   RESULT: SEQUENCES == x86, DIFFER FROM BARE (CORRECT).

The before/baseline sweep shows MANY divergences; after the fix it is 0 —
the arm64 collision conversion is now bit-identical to x86.

4. THE FIX (translation layer; goal_src 1-to-1)
-----------------------------------------------
arm64-ONLY codegen change (goalc/emitter/IGenARM64.cpp/.h, goalc/compiler/IR.cpp).
x86 codegen path (do_codegen_x86 / IGenX86_64) is byte-for-byte UNTOUCHED, so
our-x86 == original-x86 and .autoport/gold stays pristine. NO goal_src edit (the
collision GOAL source is identical to the original).
  - scalar IR_FloatToInt::do_codegen_arm64: FCVTZS Wd,Sn ; (cmp INT_MAX ; csel ->
    INT_MIN on +ovf/+Inf) ; (fcmp NaN ; csel -> INT_MIN on NaN) ; sxtw.
  - vector IR_VFMath2Asm FTOI: movi 2^31 ; fcmgt keep-mask ; FCVTZS .4s ;
    movi INT_MIN ; bif (override only the +ovf/+Inf/NaN lanes to INT_MIN).
  - new arm64 encoders csel / movi_4s_lsl24 / fcmgt_4s / bif_16b, using the
    documented-free scratch X16/X17 (GPR) and V0-V2 (NEON); no regalloc change,
    so x86 register allocation is unperturbed. The FIXED arm64 CGO set was rebuilt
    full-consistent (build_arm64_full_consistent.sh, all 28) and deployed.
