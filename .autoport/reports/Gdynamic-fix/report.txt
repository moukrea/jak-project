RESULT: DYNAMIC SCALE SEEKS MAX QUALITY AT TARGET

One-line: the adaptive render-scale controller was rewritten to the owner's EXACT
refined algorithm -- a strict single-increment (10%) HILL-CLIMB WITH A LOCK on a
SMOOTHED AVERAGE fps. It steps UP one increment while the average fps is above the
target; the moment a probe step drops the average below target it steps back DOWN
one and LOCKS at that scale -- the HIGHEST scale still holding the target (the best
quality that meets it, NOT the worst). It then STAYS locked (no per-cycle hunting)
until the average rises a sustained ~5 fps above the locked level (scene clearly
lighter), whereupon it unlocks and re-climbs. It steps DOWN one increment per cycle
while the average is below target (worst-case fluidity first). A runtime change to
the Minimum Render Scale (or the target) immediately RE-CLAMPS the running scale
into the new [floor,100] window. Proven deterministically on x86 with a closed-loop
GPU-curve seam; owner's exact repro (target 30 in a ~32fps@60% zone) converges to
60% and locks -- it is NOT stuck at the floor.

Scope: ONE file, pc/ runtime only -- goal_src/jak1/pc/pckernel-common.gc
(dynamic-render-scale-update + its state globals). No engine goal_src, no C++/libgk,
no goalc/emitter, no golden touched. libgk UNCHANGED (deploy_verify already PASS on
the C++ side). The fix is pure GOAL bytecode, identical on the x86 and arm64 backends.

--------------------------------------------------------------------------------
WHY THE PREVIOUS ATTEMPT WAS STILL "BIZARRE" (owner, 2026-07-01)
--------------------------------------------------------------------------------
Attempt 1 used a regime-split heuristic that RAISED on a frame-time / "busy" signal
in the vsync-capped regime and took PROPORTIONAL multi-step jumps. That hunted and
oscillated ("bizarre"). The owner asked for a specific, boring, correct algorithm:
a strict incremental hill-climb with a LOCK that finds the boundary once and then
sits there. This attempt implements exactly that and DELETES the busy signal and the
proportional steps entirely -- decisions are fps-vs-target only, one 10% step at a
time, on a smoothed average.

--------------------------------------------------------------------------------
THE TWO OWNER BUGS
--------------------------------------------------------------------------------
BUG 2 (headline): the controller got STUCK AT THE FLOOR (e.g. the old 10% / a 30%
  minimum) with obvious headroom. Owner repro: a "grosse scene" that at a FIXED 60%
  scale runs ~32 fps; with dynamic ON and target = 30, the scaler STAYED at the
  minimum instead of climbing to ~60% -- the WORST quality instead of the best that
  meets the target. Two root causes, both fixed:
   (a) the raise never fired with real fps headroom above target (it gated on a
       scale-independent busy signal); now it CLIMBS whenever the average fps is
       above target.
   (b) a load-driven descent to the floor used to LOCK there, so when the scene
       later lightened the lock pinned the scale at the floor WITH headroom. Now a
       LOWER only locks when it is a genuine probe overshoot (a LOWER immediately
       after a RAISE); a load-following descent stays UNLOCKED, so quality
       re-climbs by itself the moment headroom returns.

BUG 1: raising the Minimum Render Scale at runtime was not applied -- with the scale
  already dropped hard (e.g. to a 10% floor), raising the "Minimum Render Scale" to
  a higher value did not re-clamp the running/effective scale to the new floor. Now a
  runtime change to the floor (or target) snaps the running scale into the new
  [floor,100] window immediately and drops the lock so it re-converges.

--------------------------------------------------------------------------------
THE ALGORITHM (dynamic-render-scale-update, pure GOAL)
--------------------------------------------------------------------------------
  * LOWER: while the smoothed AVERAGE fps is BELOW target, step the scale DOWN ONE
      10% increment each cycle until fps >= target (worst-case fluidity first).
  * RAISE (probe up): while UNLOCKED and the average fps is ABOVE target with
      headroom, step UP ONE 10% increment and keep climbing; when a step drops the
      average below target the LOWER branch steps back down ONE and LOCKS there.
  * LOCK: once locked, HOLD -- no probing every cycle (this kills the oscillation /
      "bizarre" hunting) -- until the average rises a sustained ~5 fps ABOVE the level
      we locked at (scene clearly lighter); then UNLOCK and probe up again.
      Equilibrium = exactly ONE step below the first scale that would drop below
      target, held steady until the scene changes enough.
  * Vsync-capped target (target at/above the display refresh): fps can't exceed the
      target, so "fps holding near the cap" is the upper-headroom signal instead of
      "fps above target", so it does NOT sit stuck at the floor at a capped target.
      Still fps-only, no busy signal.
  * RE-CLAMP (bug 1): a runtime change to the Minimum Render Scale or target snaps the
      running scale into the new [floor,100] window at once and drops the lock.
  * Anti-thrash: 2nd-stage average-fps EMA (never single frames); a target-boundary
      epsilon dead-band; ONE bounded step per cooldown (>=1s raise / >=0.5s lower
      cadence); a settle before the lock reference is captured; a sustained-improvement
      gate on unlock; loads/cutscenes/menus HOLD and drop the lock; a floor clamp is
      always enforced (never below the Minimum Render Scale).
  * OFF -> returns the manual render-scale unchanged (controller idle, manual behavior
      fixed/unchanged).

PROOF -- DETERMINISTIC x86 closed-loop hill-climb (.autoport/gdfix_x86_sim.sh)
  A desktop GPU is never the bottleneck, so real fps pins at the vsync cap at every
  scale. So the controller's INERT test seam (*dyn-rs-sim-a*/*dyn-rs-sim-b*, default
  off; production reads the real pc-get-fps) is armed to SYNTHESIZE the measured fps
  from the live scale as fps = clamp(a - b*scale, [8,58]) each frame -- exactly a
  GPU-bound device (higher scale -> lower fps), closed-loop. The controller's REAL
  GOAL bytecode (identical to the arm64 build) then hill-climbs against it.
  Curve: fps = 56 - 0.4*scale, dyn-target 30  =>  40->40 50->36 60->32 70->28 ...
  So the HIGHEST scale holding fps>=30 is 60% (70% drops to 28<30) == the owner's repro.
  evidence: .autoport/reports/Gdynamic-fix/evidence/x86_sim.log
