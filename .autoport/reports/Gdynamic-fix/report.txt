THE TWO OWNER BUGS (deeper testing after Gdynamic-renderscale was owner-confirmed)
--------------------------------------------------------------------------------
BUG 2 (headline): the controller got STUCK AT THE FLOOR with obvious headroom.
  Owner repro: a "grosse scene" that at a FIXED 60% scale runs ~32 fps; with dynamic
  ON and target = 30, the scaler STAYED at the minimum (e.g. 30%) instead of climbing
  to ~60% — the WORST quality instead of the best quality that meets the target.

  ROOT CAUSE: the previous attempt RAISED the scale ONLY on frame-time headroom
  (`busy <= 0.80*budget`), never on fps-above-target. But `busy` (pc-get-frame-busy-us
  = the renderer's render_cpu_s / desktop render_game_frame CPU time) is ~SCALE-
  INDEPENDENT: render scale changes the FBO's GPU fill, not the CPU-side draw/DMA
  work. In a big (draw/CPU-heavy) scene `busy` stays near the vblank budget even at
  the floor, so the busy gate NEVER OPENS — the scale is stuck at the floor although
  fps sits well ABOVE the (low) target. (Attempt-2 had over-corrected to a busy-only
  raise to fix a vsync-capped case, and that broke the ordinary sub-cap case.)

BUG 1: raising the Minimum Render Scale at runtime was not applied — with the scale
  already dropped hard (e.g. to the 10% floor), raising the "Minimum Render Scale"
  to 30% did not re-clamp the running/effective scale to the new floor.

--------------------------------------------------------------------------------
THE FIX (dynamic-render-scale-update, regime-split, pure GOAL)
--------------------------------------------------------------------------------
Seeks the HIGHEST scale holding target. The upper-headroom signal is chosen by
regime (decided by the presentation cap = display refresh / vsync), because a
scale-independent CPU signal cannot tell "GPU has headroom" from "GPU is saturated":

  * REGIME 1 — target BELOW the cap: fps CAN rise above target, so fps IS the clean
    headroom signal. CLIMB while fps >= target+3 (the owner's core fix — do NOT sit
    at the floor when fps > target): aggressively when far above target (+10/+6),
    gently near it (+3), toward the highest scale whose fps still meets target.
  * REGIME 2 — target AT/ABOVE the cap (vsync-capped): fps saturates at the cap and
    can't exceed target, so raise on FRAME-TIME headroom (render-work comfortably
    under the vblank budget) as a gentle +4 probe; an overshoot is corrected by
    DESCEND. (Preserves the attempt-2 vsync-cap behaviour the owner had accepted.)
  * DESCEND (both regimes): fps under target by a regime-sized margin (1.0 below the
    cap, 2.5 near it). Proportional step (-12/-8/-4). NO busy gate — busy is blind to
    a GPU-bound drop; smoothed fps + margin rejects vsync jitter. So it correctly
    lowers under GPU-bound load, which the old busy-gated LOWER could have missed.

  * RE-CLAMP (BUG 1): when the Minimum Render Scale or the target changes at runtime,
    the running scale is snapped into the new [floor,100] window at once (so raising
    the floor above the current dropped scale takes effect immediately) and cooldowns
    reset so it re-converges. Equilibrium = the MAX scale meeting target.

  * ANTI-THRASH: 2nd-stage fps/busy EMAs (act on smoothed signals, never single
    frames); a target-boundary dead-band [target-1, target+3]; bounded proportional
    steps; >=0.5s lower / >=1s raise cooldowns; a >=2s post-lower raise lockout; a
    floor clamp; and a hold during loads/cutscenes/menus.
  * OFF -> returns the manual render-scale unchanged (controller idle).
