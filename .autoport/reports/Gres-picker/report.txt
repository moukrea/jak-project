Phase Gres-picker — "Game Resolution" picker: NATIVE entry + per-aspect-ratio standard ladder
=============================================================================================
RESULT: RESOLUTION PICKER NATIVE + LADDER

OWNER MANDATE (2026-06-30): the in-game "Game Resolution" option must offer, for the
CURRENT aspect ratio, a NATIVE entry (the device's real screen resolution) PLUS the
standard resolution ladder down to the minimum (640 wide if width-constrained, else
480 tall). Works on BOTH x86 and Android. A WIP existed (commit 9a1e64c84,
progress-pc.gc + pckernel-common.gc) — finish + verify it. Higher res = sharper but
LOWER fps (expected; the user chooses). Coexists with the RENDER SCALE % option.


WHAT THE WIP ALREADY DID (reviewed correct; it was never built/deployed/verified)
---------------------------------------------------------------------------------
The WIP (9a1e64c84) rewrote build-resolution-options (progress-pc.gc:1331) to build the
list from a NATIVE entry (pc-get-active-display-size -> the real panel size) + a standard
ladder GENERATED at the current aspect ratio (per-aspect compute, not a fixed table), each
entry clamped to [floor, native]; floor = 640 wide (width-constrained, the common case)
or 480 tall (height-constrained). Entries are labelled via the per-slot name-override
string ("NATIVE 2400 X 1080", "1280 X 576", ...). Verified correct on five axes before
building: the static boxed-array syntax, the ~S string format directive, the per-frame
call site in respond-common (display-state = resolution) so the list re-filters LIVE when
the aspect changes, the apply path (confirm -> set-window-size! -> commit-to-file), and
no overflow / no stale-slot bug (aspect-new options are static, name-override = #f). It
compiles + boots on x86. The "INCOMPLETE" was real but narrow: it had never been built,
deployed, or verified, and one finishing gap remained — PERSISTENCE.


THE FINISHING FIX (pc/ GOAL only; engine goal_src untouched -> gold oracle clean)
---------------------------------------------------------------------------------
PERSISTENCE of a picked resolution across a restart (commit 3c7a0b02c,
goal_src/jak1/pc/pckernel-common.gc).

Root: the settings read-path (handle-input-settings "game-size") gated the saved size on
`pc-is-supported-resolution?` — an EXACT SDL display-mode membership test
(display_manager.cpp:203). The new picker offers aspect-correct COMPUTED sizes (e.g.
1280x576 at the device's ~2.222 panel) that are NOT enumerated display modes, so on x86
this check returns the real #f for them -> the read-path snapped the pick back to native
on reload (broken persistence). On Android the helper is the no-op a17_pc_default (returns
literal 0, which in GOAL is TRUTHY, != #f), so Android already accepted any saved size;
the relaxation is harmless there and UNIFIES both builds. (Honest correction: the picker
does NOT persist on x86 without this fix; it already persisted on Android via the truthy
stub — confirmed on device by reset-gfx logging "Valid default game-size resolution set
640 x 480".)

Fix: on this single-FBO engine the game-size IS just the offscreen 3D render target (the
same lever RENDER SCALE % already drives at arbitrary sizes), so accept a saved size if it
is a real display mode OR within [PC_MIN .. native]; still reject garbage / oversized sizes
(preserves the #3563 black-screen guard). reset-gfx's conservative default (640x480 when
the panel isn't measured yet at boot) is deliberately LEFT INTACT so the DEFAULT fps is
unaffected — only an explicit user pick now survives a restart.

Also corrected the update-to-os render-scale-ORDER comment: both the picker (BASE game_res)
and RENDER SCALE % are user-adjustable on x86 AND Android and compose exactly once
(base first, then scale; render-scale clamp [10,100] so it only scales the picker's base
DOWN), never double-applied. Device confirms render-scale persisted at its 100.0 default.
