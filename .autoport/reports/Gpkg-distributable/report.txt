DESIGN (kept the PC build; changed only how its output ships + first-run UX)
================================================================================
The PC pipeline still extracts the jak1 runtime data into
  android/app/src/jak1/assets/iso_data/jak1/   (321 files: CGO/DGO/STR/VIS/SBK/...)
  android/app/src/jak1/assets/fr3/             (4 fr3 texture files)
exactly as before — that path is untouched.

What changed: the APK no longer bundles those as ~1.34 GiB of RAW, uncompressed
dirs. They are now packed into ONE DEFLATE archive that the on-device loader
DECOMPRESSES into the app-private data dir at first launch.

  1. PC build step — android/build_asset_bundle.sh (wired into Gradle as the
     bundleJak1Assets task, run before mergeJak1DebugAssets):
       packs assets/iso_data/jak1 + assets/fr3 into
       assets-bundled/bundle/jak1_assets.zip  (DEFLATE level 6, java.util.zip
       readable, single archive) + a small manifest.properties (version, file
       count, raw byte total) used to drive the progress bar, pre-check free
       storage, and verify the unpack. Idempotent: repacks only when stale.

  2. APK packaging — android/app/build.gradle.kts:
       - the jak1 assets srcDir is now assets-bundled/ (the compressed archive),
         NOT the raw src/jak1/assets dirs (which stay on disk only as the
         bundle's build input).
       - androidResources.noCompress = ["zip"] so AGP STORES the already-DEFLATE'd
         archive verbatim (re-compressing a ~1 GB compressed file buys nothing and
         walks into the mergeAssets/package GC death-spiral the raw build hit).
       - the -PslimIso fast-iteration build is preserved (fr3 only, no payload).

  3. First-run decompression UI — LoaderActivity.java (the LAUNCHER activity):
       on launch, if the on-device version stamp is absent or its version differs
       from the APK's bundle version, it streams the archive from the APK through
       java.util.zip.ZipInputStream and writes each entry to its on-device home,
       behind a one-time "Setting up game data… / Decompressing game data… NN%"
       screen with a determinate horizontal PROGRESS bar (permille of the manifest
       raw-byte total). Targets:
         iso_data/jak1/*  -> <filesDir>/iso_data/jak1/*   (fakeiso data root)
         fr3/*            -> <filesDir>/out/jak1/fr3/*     (renderer textures)

  4. Idempotent / version-stamped: a stamp file <filesDir>/.asset_bundle_stamp
     holds the bundle version. Second and later launches find the stamp, match the
     version, and boot straight to the game with NO re-decompress. A new APK that
     ships a bumped bundle version re-decompresses once.

  5. Integrity + low-storage: before unpacking, a StatFs free-space pre-check
     (raw bytes x 1.05 margin) errors out cleanly instead of filling the disk
     mid-write. During the unpack, ZipInputStream validates each entry's CRC32
     against the archive (a corrupt/truncated archive throws); after the unpack
     the loader cross-checks the written file count + byte total against the
     manifest. The stamp is written LAST, only after a fully-verified unpack, so a
     kill mid-unpack is treated as "not done" and the next launch redoes it (never
     boots off a half-written, corrupt data set).

What this is NOT: there is no file-chooser dialog, and no decompiler / transcoder
runs on the phone. The owner's earlier draft of that approach was scrapped ("would
be a massacre"); the runtime data is produced on PC and the APK is a single
owned-copy product that just decompresses its own bundled data once.
