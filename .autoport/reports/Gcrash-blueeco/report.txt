2. FORENSICS (faulting fn + PC) and CLASSIFICATION
--------------------------------------------------
From the in-fault-handler A40-DPROC dump in repro2-logcat.log (line ~4589):
  GK-DIAG sig=11 fault=0x0 pc=0x7f0018b178 lr=0x7f01e4b390
  A40-DPROC at-crash CURTHR=0x226314 tname=code pc=0x1e4b390 sp=0x1a7f40
            stack-top=0x1a8000 stack-size=128 used=192 OVER=64
  A40-DPROC at-crash mthr ... suspend-hook=0x18b014 resume-hook=0x18b2a4

- Faulting PC 0x18b178 (GOAL space) lies INSIDE the thread suspend hook
  [0x18b014..0x18b2a4] => faulting function = GOAL thread-suspend backup path
  (goal_src/jak1/kernel/gkernel.gc, the "too much stack to backup" break at gkernel.gc:607).
- The dying thread is a process CODE thread (coroutine) whose declared BACKUP-stack budget
  is 128 bytes but whose live stack use at its first suspend is 192 bytes (OVER=64).
- That budget is set by (stack-size-set! (-> self main-thread) 128) in the blue-eco vent's
  `launcher` process (goal_src/jak1/levels/common/generic-obs.gc) — the process spawned when
  Jak stands in the eco fountain.

CLASSIFICATION: arm64 STACK-SIZE class (same class as the a7c90ef2b jungle-hopper
PROCESS_STACK_SAVE_SIZE 256->512 fix). The arm64 backend's per-frame footprint is strictly
larger than x86 (mandatory STP x29,x30 = +16 B every function, 16-byte SP alignment,
asm-call brackets pushing 48 B around each blr vs the x86 call's 8 B return address), so a
coroutine that fits its declared x86 budget overflows it on arm64 and dies in
thread-suspend.

Ruled out:
- sparticle / renderer: the fault is in the kernel thread-suspend path on the code thread,
  not in any draw/DMA builder; render stream was healthy up to the fault.
- the OLD blue-eco PORTAL crash (arm64 float-compare divergence, fixed earlier — owner
  already plays past portals) — different site, different mechanism; it is NOT the cause.
- jungle hopper stack crash (a7c90ef2b): that fixed the C++ PROCESS_STACK_SAVE default;
  this crash is the GOAL-side per-process constant path, which that fix does not reach.
- background sig9 / OOM: crash signal is sig=11 with an in-process fault-handler dump.

3. FIX (1-to-1, translation layer only)
---------------------------------------
goalc/compiler/compilation/Function.cpp:339-358 (commit c91304925), compiler codegen layer:
when (and ONLY when) compiling for InstructionSet::ARM64, every constant N in
(stack-size-set! thread N) is doubled at compile time (128 -> 256 for the blue-eco
launcher, covering the measured 192-byte arm64 depth with margin). Same remedy class as the
a7c90ef2b PROCESS_STACK_SAVE_SIZE 256->512 intercept. Costs at most the same again out of
each process's >=16 KiB heap.

goal_src (engine) is UNTOUCHED; game/kernel/jak1/kmachine.cpp gained only the debug-only
LEVEL-WARP-POS repro aid (inert unless the debug prop/env is set). No goalc/emitter or
IGenX86_64 change. .autoport/gold untouched (pristine).

x86 1-to-1 PROOF (byte identity): full x86 CGO/DGO rebuild WITH the fix vs WITHOUT:
sha256 of ALL 28 files IDENTICAL (/tmp/x86-withfix.sha == /tmp/x86-prefix.sha, verified
2026-07-02 19:58). The arm64 rebuild differs as expected (stack constants doubled). The
post-fix arm64 set is stored at .autoport/backups/jungle-arm64-blueeco (sha256 set ==
/tmp/arm64-withfix.sha == /tmp/blueeco-set.sha).
