## The fix (game/kernel/jak1/klink.cpp, jak1_finish)
Root cause identical to jak2 (98ef5f669): link_control::jak1_jak2_begin (common/klink.cpp:1197)
sets m_code_size = 0 on the opengoal v3 path and never assigns it ("todo, set m_code_size"
at common/klink.cpp:1228), so jak1_finish's CacheFlush(m_code_start.c(), m_code_size) was
CacheFlush(base, 0) — a no-op. The v3 TOP_LEVEL segment is re-allocated at the SAME reused
KMALLOC_TOP address for consecutive objects and executed immediately after being rewritten,
so the arm64 icache could serve a stale mix of the PREVIOUS object's instructions.
Fix = exact jak2_finish pattern: real-range CacheFlush over code_infos[MAIN, TOP_LEVEL,
DEBUG] (offset&&size guarded) for v3 objects, CacheFlush(m_object_data, m_code_size) for
v2/v4. On arm64 builds CacheFlush is __builtin___clear_cache(mem, mem+size)
(android/android_runtime_compat.cpp:388, game/linux-arm64 + game/android-arm64 compat TUs);
the x86 CacheFlush body (kmachine.cpp:127) is a no-op, so the x86 path is unchanged.
Engine goal_src untouched; assets untouched (C++-only fix, no codegen change).
