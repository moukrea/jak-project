Gtouch-fix — touch menus: ALL option types tap-drivable (toggles, sliders, save rows, carousels)

RESULT: ALL MENU ELEMENTS TAPPABLE

## Root cause (why sub-elements were tap-dead while main rows worked)
The Gtouch-menus tap layer replayed a tap as synthetic d-pad presses, but its per-type
sequences only really worked for menu/button rows:
1. ON/OFF TOGGLES: in respond-common, d-pad LEFT means absolute ON and RIGHT means absolute
   OFF. The old positional mapping (tap-half -> LEFT/RIGHT) therefore NO-OP'd whenever the
   tapped half matched the current value — the owner's "toggles not clickable".
2. SLIDERS: unselected sliders drew ONLY their name (no value), so even a working step gave
   zero visible feedback; the old 3-steps-per-tap hold-token sequence was also unreliable.
   The owner's "sliders not clickable at all".
3. SAVE-FILE SCREENS (load-game / save-game / save-game-title): respond-memcard consumes
   confirm from cpad x/circle ONLY — the touch confirm flag was never read there, so a tap
   could focus but never ACTIVATE ("CONTINUE WITHOUT SAVING" only focused). Additionally the
   4 memcard slot boxes are drawn by the locked engine draw-memcard-file-select (nameless
   button rows), so they were never published to the tap hit-test at all.
4. LONG LISTS: rows past the visible page (V-Sync, MSAA, Advanced Settings, Back on Graphic
   Options) were unreachable by touch — no way to scroll by tap.
5. YES-NO dialogs: a tap only set the choice, never confirmed it.

## Fix (goal_src/jak1/pc/progress-pc.gc ONLY — pc layer; engine goal_src untouched)
- on-off / normal-inverted / aspect-native / two-state aspect-ratio / cheat-toggle rows:
  one tap = FLIP; direction derived from the CURRENT value (reads value-to-modify / cheats
  bitfield), seq = CONFIRM + dir + CONFIRM.
- slider rows: one tap = ONE step (left half steps down / right half steps up, repeated taps
  keep stepping), seq = CONFIRM + hold-dir + CONFIRM; unselected sliders now display their
  CURRENT VALUE inline ("MIN RENDER SCALE: 70") so every step is visible.
- memcard screens: respond-memcard ORs in the touch confirm flag (and consumes it), so a tap
  on the focused row ACTIVATES it (focus+activate in one tap); the 4 slot boxes are published
  to the hit-test with measured geometry (slot k center at normalized y = 0.1838 + 0.1831k).
- yes-no dialog rows: tap = choice (left half YES / right half NO) + CONFIRM in one tap.
- tap-scroll: on lists longer than the page, a tap below/above the visible rows emits a
  synthetic d-pad DOWN/UP (new MT_TOK_UP/DOWN tokens ORed into the respond-common up/down
  guards). These zones are checked BEFORE the row hit-test (the row acceptance band swallowed
  the below-list zone otherwise — this ordering bug is what sent attempt 2's blind verify
  off the rails).
- stale-sequence guard: a screen change kills any in-flight synthetic token queue
  (seq-screen field) so leftover tokens can't replay as phantom presses on the new screen.
