WHERE THE REAL INPUT IS DROPPED (the named drop point)
------------------------------------------------------
The record TAP (android_runtime_compat.cpp::CPadGetData -> pad_replay::on_cpad_read) records
exactly what android_input_audio::get_cpad_state() returns — the MERGE of the touch-overlay /
gamepad producers (g_overlay_button0 / g_stick_*) OR the headless injector (g_inject_*). The
merge + record + replay path is SOUND (see THE AFTER: adb-input touch records 77%). The
all-neutral is a SILENT INPUT-DELIVERY failure BEFORE the merge: the owner's active input
source never reaches on_pad_button / on_pad_axis -> g_overlay_button0 / g_stick_*, so
get_cpad_state returns neutral and the tap records all-neutral. Two real conditions cause it,
both rooted in the touch overlay being REMOVED from touch hit-testing:
  1. When a gamepad is present at first launch, MainActivity defaults PREF_TOUCH_OVERLAY_ENABLED
     to false and the overlay is NEVER ADDED (setupTouchOverlay early-returns).
  2. The gamepad auto-hide sets the overlay to View.GONE — GONE removes it from touch
     hit-testing entirely (confirmed: overlay-actuate=0, recorded 0/602).
With the overlay removed AND a Bluetooth gamepad that is bonded-but-not-delivering Android
input events (a common Switch Pro / DualShock quirk), there is NO input path at all and the
record is SILENTLY all-neutral — the owner's wasted 20-min / 90-min captures.

================================================================================
THE FIX (host/runtime only; goal_src 1-to-1; no goalc/emitter change)
================================================================================
Guarantee a capturable input path whenever a record/replay is armed
(android/app/src/main/java/org/opengoal/gk/MainActivity.java + TouchOverlayView.java):
  * MainActivity.setupTouchOverlay(): when debug.opengoal.pad_replay = record|replay (read
    via getprop at onCreate — it is set before launch), FORCE the touch overlay ON even if
    the gamepad/user default disabled it, so a record always has a recordable touch input.
  * MainActivity.pollGamepadCount(): while a record/replay is armed, do NOT View.GONE the
    overlay on gamepad-detect — keep it touch-capable (GONE would re-introduce the drop).
  * TouchOverlayView.setPersistentVisible(): while armed, keep the controls visible (no
    10s idle fade) so the owner SEES and uses the touch controls to record, even if their
    Bluetooth gamepad is silent.
The merge, the record tap, the logic-frame index, the anchor and the RNG reseed are all
UNCHANGED — determinism is unaffected (the change is purely which Java input source is alive).
