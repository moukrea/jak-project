1. WHAT EXISTED UPSTREAM vs WHAT I WIRED  (the phase premise was FALSE for this checkout)
====================================================================================================
The phase brief assumed "Upstream OpenGOAL already has a Vulkan renderer tree — wire it up." THAT IS
FALSE for this repo:
  - There is NO game/graphics/vulkan_renderer/ (or any Vulkan renderer) in the tree.
  - `git log --all` for a Vulkan renderer / GfxPipeline::Vulkan returns NOTHING — it never existed here.
  - The only "vulkan" in the tree is inside SDL3 itself (SDL's own GPU/render backends + Khronos headers).
  - The game renders through 47,315 lines across 101 files of RAW OpenGL (every bucket renderer:
    tfrag/tie/merc/sprite/sky/ocean/shadow/eye/direct/...) plus dozens of GLSL shaders. Porting that to
    Vulkan (explicit pipelines/descriptors/sync + GLSL->SPIR-V), on two platforms, oracle-matched, is a
    multi-person multi-month effort — categorically infeasible in one phase.
There WAS one useful remnant: pc-settings already declared an (unused) enum `pc-gfx-renderer`
{software, opengl, vulkan, direct3d} and a `gfx-renderer` field (the read-deserializer worked; the
write was commented out). I reused that.

What I wired instead (the real, shippable increment): the full backend-SELECTION infrastructure both
builds need, a menu option, and a genuine minimal Vulkan RUNTIME on x86 (SDL_gpu) to prove the Vulkan
surface/present path — de-risking the future full port.

3. CORRECTNESS — which build got Vulkan, and how it was verified (oracle vs GL)
====================================================================================================
x86 DESKTOP — Vulkan LIVE (verified, this run):
  - Default (renderer=0): boots to "link finish: logo", log shows OpenGL 4.6 (Mesa), NO "[Vulkan]" line.
    => GL default path CORRECT and UNCHANGED.
  - Vulkan (renderer=1): log shows "[Vulkan] SDL_gpu device up (driver: vulkan)", reaches
    "link finish: logo", continues to "logo-intro-2" at ~60fps, ZERO Vulkan/swapchain errors. The engine
    only advances because vk_vsync is woken by each Vulkan present -> the acquire+clear+present loop is
    genuinely live.
  - CORRECTNESS SCOPE: the Vulkan PRESENT path is correct and proven. It presents a CLEARED surface, not
    the scene: the OpenGL bucket renderers are not ported, so send_chain (the game DMA chain) is a no-op.
    Therefore a full-scene oracle-diff vs the GL path (side-by-side pixel match of the title / a gameplay
    scene) is DEFERRED — there is no Vulkan-drawn scene to compare yet. This is stated plainly rather than
    faked: selecting Vulkan today gives a working Vulkan window, not GL-equivalent frames.

ANDROID — menu option present, Vulkan RUNTIME DEFERRED:
  - Android bypasses the desktop GfxPipeline path entirely (Gfx::Init is a no-op stub; the GLES module is
    hardcoded). Wiring a Vulkan surface/renderer into the Android native pipeline is a follow-up; I did
    NOT risk the working GLES build for it. The shared GOAL menu still SHOWS the option on Android and it
    persists, but the build keeps rendering with GLES. Clearly a deferred, labeled partial.
  - SAFETY: an unbound pc-* symbol on Android = BLR into a null slot = SIGILL. Android's pc-port table is
    a17_bind_pc_helpers() in gk_android_main.cpp (common/kmachine.cpp is NOT compiled on Android), so I
    bound pc-set-gfx-renderer! there to a17_pc_default (no-op) — the toggle is safe on device (no crash);
    the state still persists GOAL-side.
