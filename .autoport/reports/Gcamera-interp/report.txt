--------------------------------------------------------------------------------
0. TL;DR
--------------------------------------------------------------------------------
Attempt 1 (make ALL motion scale by the fractional real-frame time — a GLOBAL
timestep change) was REVERTED: the owner reported it was the wrong lever (camera
still choppy, same or worse, fps regressed) with the decisive signal that the
world/Jak move SMOOTHLY and ONLY the camera juders. A global change would judder
everything together, so it cannot be the mechanism. This attempt is CAMERA-ONLY,
pure render-time, with the game clock / world motion / physics untouched.

Root cause (traced in code, confirmed on device): at sub-target fps the engine's
per-frame INTEGER time-ratio k must dither (e.g. hist {1,2,3,4}, mean ~1.74 at
~34fps in Geyser at full render scale) to keep the game clock exact. The camera pan
and the world/Jak motion are integrated against the SAME quantized clock (camera
pan uses (seconds-per-frame); the follow spring uses (time-adjust-ratio); Jak's
step-collison! uses the identical (* ... seconds-per-frame)) — so there is NO
"camera rides a different clock" bug. The ±half-frame quantization STEP is only
VISIBLE on the camera because a pan sweeps the WHOLE viewport at high angular speed,
while the same step hides in slower/animated world motion. It is temporal-aliasing
amplified by the pan, not a factor mismatch.

Fix: render the camera at the correct FRACTIONAL (sub-frame) time. In update-camera,
after the final camera pose is built and BEFORE the view/projection matrices are
rebuilt, interpolate the DISPLAYED camera pose BETWEEN the last two LOGIC-FRAME
poses (this frame's raw pose and the previous rendered frame's raw pose) by the
sub-frame residual so the displayed camera samples the trajectory at EVENLY-spaced
game-times => constant on-screen angular velocity. No global timestep, no 30/60
lock, no game-speed change; FrameLimiter fix intact.

--------------------------------------------------------------------------------
1. WHAT THE PC/ORIGINAL DOES TO STAY SMOOTH (and why Android steps)
--------------------------------------------------------------------------------
* display-frame-start (drawable.gc:969-997) computes time-ratio as an INTEGER
  (the float (+ (/ (timer-count ...) *ticks-per-frame*) 1)) and PC-snaps
  float_time_ratio < 1.3 -> 1.0. set-time-ratios (display.gc:35-62) derives
  seconds-per-frame = ratio/target-fps and time-adjust-ratio = (60/target-fps)*ratio
  from that SAME integer. So the per-frame motion step is quantized to whole k.
* PC/x86 (the original): vsync + the desktop FrameLimiter pin every frame to
  ~1/target-fps, and the game runs at a HIGH, EVEN fps (typically the 60 target),
  so float_time_ratio stays < 1.3 and the integer ratio is a CONSTANT k == 1 — the
  camera advances the same small delta every frame = smooth. The PC does NOT
  interpolate the camera; it simply runs the logic at an even, locked rate. There
  is no render-vs-logic split on desktop (render == logic; math-camera is built
  from the current camera state only).
* Android at Geyser, full render scale: the device is render-bound at ~33-35fps and
  cannot hit 60, so the error-feedback frame clock (gk_android_main.cpp
  a35_gfps_frame_tick) must emit k dithering across {1,2,3,4} to keep game-time
  exact — the integer STEP that reads as camera-pan judder. This is the case the PC
  never enters (it is above target with k == 1).

--------------------------------------------------------------------------------
2. THE FIX — camera-only render-time sub-frame interpolation
--------------------------------------------------------------------------------
Android frame clock publishes a sub-frame residual (pc-camera-subframe, micro-units):
    beta = (k - fractional_time_ratio) / k    in [-0.5, 0.5]
Algebraically this equals (g_gfps_emitted - g_gfps_desired)/k — the ACCUMULATED
phase by which the emitted integer game-time leads the smooth real-time-integrated
demand (g_gfps_desired += real_dt * target_fps), expressed as a fraction of this
frame's k-step. 0 on x86 and when the A/B toggle debug.opengoal.caminterp=0 => no-op.

In update-camera (cam-update.gc), camera-interp-retime does, Android-only:
    pose_display.trans        = vector-lerp!(raw_pose[n], raw_pose[n-1], beta)
    pose_display.inv-cam-rot  = quaternion-slerp!(raw_pose[n], raw_pose[n-1], beta)
then stashes raw_pose[n] for next frame. lerp/slerp(pose[n], pose[n-1], beta) samples
the camera trajectory at game-time  emitted[n] - beta*k = g_gfps_desired  — and
g_gfps_desired advances by a CONSTANT amount per real frame at steady fps, so the
DISPLAYED camera advances by an EVEN angular step (constant real-time velocity)
regardless of the k dither. Worked example (steady 40fps, k dithers 2,1,2,1): raw
per-frame yaw deltas 2,1,2,1 (the owner's "step") -> displayed deltas 1.5,1.5,1.5,1.5
(the exact ideal real-time progression). Guards: no-op on the first frame, on a
camera cut (math-camera reset, set by cam-master.gc:681), and on a >160m teleport.
Runs on the FINAL pose for ALL camera modes, BEFORE matrix-transpose/camera-temp/
frustum-plane rebuild, so the rebuild recomputes everything from the re-timed pose.
The existing smooth-t block already uses matrix->quaternion/quaternion-slerp!/
quaternion->matrix on-device, so the arm64 codegen path is proven.

--------------------------------------------------------------------------------
4. HOLDS UNDER DYNAMIC RENDER SCALE / VARIABLE FRAME TIMING
--------------------------------------------------------------------------------
The re-time is driven by g_gfps_desired = accumulated (real_dt * target_fps), i.e.
it INTEGRATES the actual per-frame wall-clock time — so variable frame timing is its
INPUT, not a failure mode. The primary measurement above is itself under VARIABLE
frame timing: present-fps dt sd = 5.3-7.7 ms on a ~29-30 ms frame (the frames are
NOT vsync-even), and the interp reduced jerk under exactly that jitter. Dynamic
render scale only changes fps/frame-timing (and, when it holds a target, makes k
MORE constant = LESS dither = an easier case); the fixed-scale-100 sub-60 regime
measured here is the HARDER case (maximal k dither, {1,2,3,4}). The re-time therefore
holds under dynamic render scale — the identical resample-to-g_gfps_desired runs
whatever the source of the timing variation.

--------------------------------------------------------------------------------
5. GAME SPEED UNAFFECTED + FRAMELIMITER FIX INTACT
--------------------------------------------------------------------------------
The fix is PURE render-time: it writes ONLY *math-camera* trans + inv-camera-rot
right before the render matrices are rebuilt, and NEVER touches base-frame-counter /
integral-frame-counter (the game clock) or the Gcamera-smooth FrameLimiter busy-spin
(unchanged). Game speed is therefore constant by construction, and the A/B
base-frames/real-sec are IDENTICAL off vs on (300.5 vs 300.1 / 300.0). Constant game
speed confirmed; FrameLimiter fix intact.
