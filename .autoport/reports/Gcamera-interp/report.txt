--------------------------------------------------------------------------------
0. TL;DR
--------------------------------------------------------------------------------
Attempt 1 (make ALL motion scale by the fractional real-frame time — a GLOBAL
timestep change) was REVERTED: the owner reported it was the wrong lever (camera
still choppy, same or worse, and fps regressed), with the decisive signal that the
world/Jak move SMOOTHLY and ONLY the camera juders. A global change would judder
everything together, so it cannot be the mechanism.

Root cause (camera-specific, code + device data): at sub-target fps the engine's
per-frame INTEGER time-ratio k must dither (e.g. 2,3,2,3 at ~22fps in Geyser at
full render scale) to keep the game clock exact. EVERY motion advances by that
quantized game-time step, but the ±half-frame temporal-aliasing STEP is only
VISIBLE on the camera, because a pan sweeps the WHOLE viewport at high angular
speed while the same step hides in slower/smaller world motion and in Jak's
physics-integrated movement. The PC/original never shows it because vsync +
FrameLimiter pin every frame to exactly 1/target-fps, so k is a constant 1 — the
PC does NOT interpolate the camera, it simply runs the logic at an even locked
rate so the per-frame delta is constant.

FIX (camera-scoped, PURE render-time; no global timestep, no 30/60 lock, no
game-speed change, FrameLimiter fix intact): in update-camera, after the final
camera pose is built and BEFORE the view/projection matrices are rebuilt,
interpolate the DISPLAYED camera pose between this frame's and the last frame's
RAW logic poses by the sub-frame quantization residual
    beta = (k - fractional_time_ratio)/k   in [-0.5, 0.5]
(published by the Android frame clock as pc-camera-subframe; 0 on x86 / when the
A/B toggle is off => no-op). The existing rebuild then recomputes camera-rot /
camera-temp / frustum planes from the re-timed pose. This makes the on-screen
camera advance by REAL elapsed time (even angular velocity) instead of the integer
step — worked example (steady 40fps, k dithers 2,1,2,1): raw per-frame yaw deltas
2,1,2,1 (the owner's "step") become displayed deltas 1.5,1.5,1.5,1.5 (the exact
ideal real-time progression). Only *math-camera* (the RENDER camera) is touched;
the game clock (base/integral-frame-counter), world motion, physics, and the
camera LOGIC are all untouched.

--------------------------------------------------------------------------------
1. WHAT THE PC/ORIGINAL DOES TO STAY SMOOTH (and why Android steps)
--------------------------------------------------------------------------------
* display-frame-start (drawable.gc:969-1029) computes an INTEGER time-ratio and
  PC-snaps float_time_ratio<1.3 -> 1.0; set-time-ratios (display.gc:35-62) derives
  seconds-per-frame = ratio/target-fps and time-adjust-ratio = (60/target-fps)*ratio
  from it. The camera pan (cam-states.gc cam-string-joystick) and the follow
  spring (camera.gc) scale by these SAME quantities the world uses — so there is
  no "camera rides a different clock" bug; the difference is VISIBILITY/amplitude.
* PC/x86: vsync + the desktop FrameLimiter (common/util/FrameLimiter.cpp, called in
  opengl.cpp before SwapWindow) pin each frame to exactly 1/target-fps, so the
  elapsed timer == *ticks-per-frame* and the integer ratio is a constant 1.0 =>
  the camera advances the SAME small delta every frame = smooth. There is NO
  render-time interpolation on desktop (verified: render == logic, math-camera is
  built from the CURRENT camera state only, cam-update.gc / math-camera.gc).
* Android at Geyser full render scale: the device is render-bound at ~22fps, cannot
  hit 60, so the error-feedback frame clock (gk_android_main.cpp a35_gfps_frame_tick)
  must emit k in {2,3} each frame — the integer STEP that reads as camera-pan judder.

3. HOLDS UNDER DYNAMIC RENDER SCALE / VARIABLE FRAME TIMING
--------------------------------------------------------------------------------
The re-time is driven by the per-frame real dt (variable frame timing IS its
input), so it works at any/variable fps. PENDING dynamic-scale confirmation run.

--------------------------------------------------------------------------------
4. GAME SPEED UNAFFECTED + FRAMELIMITER FIX INTACT
--------------------------------------------------------------------------------
The fix is PURE render-time: it writes ONLY *math-camera* trans + inv-camera-rot
right before the render matrices are rebuilt, and NEVER touches base-frame-counter
/ integral-frame-counter (the game clock) or the Gcamera-smooth FrameLimiter
busy-spin (android_gfx.cpp / opengl.cpp, unchanged). Game speed is therefore
constant by construction; the A/B base-frames/real-sec above are identical off/on.
