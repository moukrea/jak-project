0. TL;DR
--------------------------------------------------------------------------------
* ROOT (confirmed by attempt-3, not re-litigated): at sub-60fps the Android frame
  clock's integer time-ratio k DITHERS 1<->2<->3 every frame (game time is kept real
  by advancing k 60Hz-ticks per rendered frame). The camera's per-frame angular
  advance is proportional to k, so a right-stick pan lurches +1x,+2x,+1x... = judder.
  The arm64 camera MATRIX math is BIT-IDENTICAL to the x86 GOLDEN (attempt-3 replay,
  deltas <= ~1 ULP) -- this is NOT a numerical/codegen divergence, it is a TIMING
  quantization. World/Jak motion is slow + physics-damped so the same half-frame
  lurch is hidden there: "action fluide, camera choppy".

* WHAT THE PC/ORIGINAL DOES to stay smooth: it runs the logic at a LOCKED 60fps, so
  k is a CONSTANT 1 -> the camera advances the SAME delta every frame -> smooth.
  There is no interpolation on the original; it simply never dithers k. On Android
  many devices cannot hold 60fps (owner: "le 60 FPS toutes les devices vont pas
  pouvoir atteindre"), so k must dither to keep game-time real, and the camera juders.

* THE FIX (this phase) = classic fixed-timestep RENDER INTERPOLATION, camera-pose
  only, replicating the original's even per-frame advance at ANY fps:
    - The game logic still runs at integer k (untouched -> speed constant, no fps cost).
    - At RENDER time, the render-facing camera pose (*math-camera* trans + view
      rotation) is interpolated between the PREVIOUS and CURRENT logic-frame pose by a
      sub-frame alpha, so the DISPLAYED camera sits at real cumulative display time,
      which advances evenly -> smooth, independent of the k-dither.
    - alpha = (deficit - 0.5) / k, strictly CLAMPED [0,1] (RENDER-ONLY; NEVER
      extrapolates). deficit/k is the real-time fraction within this frame's k-tick
      step; the -0.5 half-tick lag makes alpha land in [0,1] for every k WITHOUT the
      clamp having to fire (since k = round(deficit) => |deficit-k| <= 0.5), so the
      rendered cumulative-time advances perfectly evenly and never overshoots the
      current pose. (A plain deficit/k overshot when the device ran a hair behind
      schedule; the [0,1] clamp then pinned those frames to the current pose,
      reintroducing an uneven step -- measured, then removed by the -0.5 lag: it
      roughly HALVED the residual jump metric, 0.16 -> 0.08.)

* DEVICE, state-anchored, DRIFT-FREE A/B (the honest measurement): one deployed
  binary; toggle debug.opengoal.caminterp 0<->1 every 5s DURING one continuous
  injected right-stick pan (pad_replay cpad injection, Jak stationary, open Geyser

1. WHERE THE FIX LIVES (and why it is render-only + consistent)
--------------------------------------------------------------------------------
There is NO C++ chokepoint for the camera: every ported renderer reads its camera
matrices from GOAL-built DMA packets that copy *math-camera* fields (tfrag/background
add-pc-tfrag3-data -> background_common.cpp; merc m_low_memory). The single point
that feeds them all is *math-camera* itself, finalized once per frame in update-camera
(cam-update.gc), which runs BEFORE the draw builds those packets. So the fix belongs
in GOAL, at *math-camera*, right after the raw pose is written and BEFORE the view/
projection matrices are rebuilt.

Files:
  * goal_src/jak1/engine/camera/cam-update.gc  (DOCUMENTED ENGINE CHANGE, see below)
      - new cam-render-interp!: snapshots the RAW current pose (trans + view rotation
        as a quaternion), and IF interpolation applies, replaces *math-camera* trans
        (vector-lerp) and inv-camera-rot rows 0-2 (quaternion-slerp, shortest-path)
        with the prev->curr interpolation by alpha; then stores the RAW current pose
        as next frame's prev. Called between the mode cond (raw pose written) and
        matrix-transpose! (camera-rot/camera-temp rebuild), so camera-rot, camera-temp,
        prev-camera-temp and the frustum planes all re-derive consistently from the
        interpolated pose. Render-only: the camera process keeps its authoritative
        state; *math-camera* is a render-facing OUTPUT and is not read back into camera
        integration. Interpolation GATE (snap = no interp): first frame, alpha>=0.999,
        alpha<=0, *math-camera* reset (hard cut), (movie?), teleport (>10 m or >~16 deg
        angular cut), and any non-gameplay camera (look-through-other/external) -- this
        last exclusion keeps the title/scripted/cut cameras byte-identical (the
        attempt-2 title regression fix).
  * goal_src/jak1/pc/pckernel-h.gc         : (define-extern pc-camera-interp-alpha ...)
  * android/gk_android_main.cpp            : a35_gfps_frame_tick publishes alpha =
        clamp((deficit-0.5)/k, 0,1) in micro-units; a35_pc_camera_interp_alpha exposes
        it; bound in a17_bind_pc_helpers. A/B toggle debug.opengoal.caminterp.
  * game/kernel/common/kmachine.cpp        : desktop/x86 stub pc_camera_interp_alpha()
        returns 1e6 (alpha 1.0) and is bound only #ifndef __ANDROID__, so on x86 the
        interp is skipped entirely -> x86 render byte-identical (see 1-to-1 note).

1-to-1 / DOCUMENTED ENGINE CHANGE justification: the only engine goal_src edit is
cam-update.gc. It has NO C++ chokepoint alternative (camera baked into GOAL DMA), so
the render interpolation must live in GOAL, exactly as the owner specified ("interpolate
... after the pose is built and before the view/projection matrices"). It is Android-
runtime-gated: pc-camera-interp-alpha returns 1.0 on x86/desktop -> the interp guard
(< alpha 0.999) fails -> *math-camera* is untouched -> the x86 RENDER is byte-identical
to the original. Only the (variable-fps) Android path interpolates. This preserves
our-x86 == original-x86 at runtime.

--------------------------------------------------------------------------------
2. WHY THE ALPHA IS CORRECT (renders at even real display time; PC/original match)
--------------------------------------------------------------------------------
The Android clock (gk_android_main.cpp a35_gfps_frame_tick) tracks, per frame,
g_gfps_desired (cumulative real display time in 60Hz ticks) and g_gfps_emitted
(cumulative integer ticks where *math-camera* actually sits). Rendering the pose at
cumulative time R = desired - 0.5 (via alpha = (deficit-0.5)/k between prev=emitted-k
and curr=emitted) makes the DISPLAYED camera advance by the real per-frame time every
frame -> even -> smooth, exactly like the PC/original's constant-k advance at locked
60fps. The k computed each frame drives the NEXT frame's time-ratio and update-camera
reads this alpha next frame -> the alpha and the pose it interpolates are aligned. At a
locked 60/30fps k is constant and the motion is already even (the interp adds only a
harmless ~8ms constant lag); the smoothing benefit appears exactly where k dithers
(sub-60fps), which is the owner's case. No extrapolation ever (alpha in [0,1]).

is logged (PACE-EE) and scored for per-frame step continuity. The DRIFT-FREE A/B
toggles caminterp within ONE run so OFF and ON share the fps/thermal state.

Reference/original comparison: attempt-3's deterministic replay proved the arm64
camera pose is BIT-COMPARABLE to the x86 GOLDEN under a constant timestep (the math is
not diverging); the ONLY difference device-vs-original is the k-dither timing, which
the PC/original avoids by locking 60fps. This fix reproduces the original's even
per-frame camera advance on Android at any fps by interpolating the render pose to real
display time -- turning the device's uneven per-frame camera-delta (OFF, jump>1.5x
0.18) into a continuous one (ON, jump>1.5x 0.08).
