The bunched layer the prior PART-proxy false-greens MISSED is the menu's ModeHUD user-hvdf icon/

so the sprite3_3d shader (sprite_3d.vert:134) used the GLOBAL hud_hvdf_offset (screen-centre)

=== ARM64 ROOT CAUSE (why the matrix index was 0 on device) ===
mips2c sp-launch-particles-var (game/mips2c/jak1_functions/sparticle_launcher.cpp) has an is-3d
guard `beq s6, s7` ("is (-> system is-3d) == #f? then SKIP sp-euler-convert") that gates whether a
2D screen-space sprite runs sp-euler-convert. s6 = system.is-3d (loaded via lw -> the bare low-32
GOAL offset 0x14fd24 for #f); s7 = #f (the full host symbol base 0x7f0014fd24). On arm64 a full-64
sgpr64 compare MISSES #f, so the branch does NOT fire and a 2D menu particle WRONGLY runs
sp-euler-convert, which rebuilds the staging sprite's flag-rot-sy from euler angles and OVERWRITES
flag-rot-sy.y (= the user-hvdf matrix INDEX, written correctly at block_22) with ~0 rotation data.
x86's sgpr64 compare correctly detects #f and SKIPS sp-euler-convert, so the index survives.
FIX (translation layer, arm64-only): compare the representation-agnostic 32-bit GOAL pointer
(gpr_addr) — sparticle_launcher.cpp ~589. Same #f-guard bug class as the is-3d fix at line ~363
and the GNG/Gbirds fixes. goal_src untouched (1-to-1); our-x86 == original-x86.
