3b. HOW THE RESIDUAL IS CLEARED — REWRITTEN (C14c), because the first shape did not converge.
   The previous resolve pushed the LINK out along the worst volume's normal, per SAMPLE, up to
   three times, bounded per push. On the 09:46 device run it bought 5%: jak-hd ended a frame at
   meshpen=475.15 out of mraw=502.55, and dax-hd sat at 537.5458 in two different legs — the
   same value twice, i.e. a fixed configuration it could never climb out of. Two structural
   reasons, neither of them tuning:
     * a push out of volume A lands the sample inside neighbouring volume B and the next
       iteration pushes it back into A. The normals disagree; the iteration orbits instead of
       converging. This is also why meshpen could read HIGHER than mraw (537 > 502): the
       resolve was making some samples worse, which is precisely "une resolution plus genante
       que le clipping".
     * the samples of one link fight each other. Each shoves the shared link origin, so the
       sample resolved first is silently un-resolved by the one resolved last — and only the
       last one's residual was ever re-measured.
   Both disappear if the search is made ONE-DIMENSIONAL and aimed at a known-feasible end. The
   authored pose is that end: with the link origin at *phys-targ*, every sample's test point
   and its own authored floor point are THE SAME POINT, so the effective penetration is exactly
   0 against every body volume simultaneously. The resolve now bisects the segment
   [authored pose -> simulated pose] (6 steps) for the LARGEST fraction of the physics
   deviation that is still clear, and commits that, velocity-neutrally (prev travels with the
   correction, rule O). Properties by construction rather than by hope:
     * it always terminates and always finds a feasible commit — t=0 is feasible by definition;
     * it never overshoots into a neighbouring volume, because it only ever moves TOWARD the
       authored pose and never past it;
     * it keeps every part of the motion that was not the problem — a chest jiggling outward is
       untouched, only travel that goes INTO the body is trimmed;
     * meshpen <= tolerance is therefore a GUARANTEE, not an outcome, which is what "ne doivent
       pas passer au travers du mesh de leur personnage, QU'IMPORTE LA RAISON" actually asks for.
   It is also cheaper: 6 probes replace up to 15 push-and-re-audit rounds per link.
   What this changes about the positive control is stated in its own section below, not hidden.

4. RESOLUTION SMOOTHNESS (C14-D). "Un truc tente d'empecher les meches de clipper dans ses
   oreilles mais ca fait des trucs BIZARRES plus genants qu'un simple clipping." A resolution
   the eye reads as a jump is worse than the clip it replaced. `resjerk` = the worst
   single-frame NET resolution displacement any link took — the length of the VECTOR sum of
   every correction every pass applied to it that frame (substep sweep, final sweep,
   cross-side, model fallback, strand pass, mesh sweep), reported per window and bounded on
   every leg.
   INSTRUMENT CHANGE, STATED OPENLY — THE SECOND ONE, and this time the metric is refuted by
   its own arithmetic rather than by taste. History first, because it matters: the ledger began
   as a sum of correction MAGNITUDES and a link at rest, visually motionless, read a resjerk of
   100853 on
   a window whose every calm gate was green. That was corrected to a sum of correction VECTORS,
   on the reasoning that opposing corrections would then cancel. They do not, and the 09:46 run
   shows why in one line — jak-hd's worst window read

       resjerk = 66389.27   while   maxdev = 1031.47

   a claimed 16-metre single-frame jump by a bone that never left a 25 cm neighbourhood of its
   own authored pose all window. The vector sum cannot cancel because the force that UNDOES a
   correction is the SPRING, and the spring never writes to the ledger: the sum only ever sees
   one side of the argument, so it grows monotonically while the bone goes nowhere. It was also
   blind in the other direction — the model-pose ladder, the escape pass and the length restore
   all move out/pos/prev and never touched it at all.
   The declaration always stated the right definition ("where the bone ENDED the frame relative
   to where resolution found it"); it was never what the code computed. It is now: resjerk is
   the worst single-frame change in a link's OFFSET FROM ITS AUTHORED POSE. Differencing
   against the authored pose divides out the character's own travel — an actor crossing 4032
   units in a frame carries his hair with him, and that is not a snap — and leaves exactly the
   artifact the owner described: the physics offset changing discontinuously. A settled link
   holds its offset and reads ~0; an honest swing reads its own per-frame travel (maxvel, ~117
   on that same window); a real one-frame jolt reads its full visible size. It is strictly MORE
   complete than the ledger (it sees every pass, including the three that never wrote to it),
   and it cannot be satisfied by killing the sim, because the locomotion FLOORS are graded on
   this same execution. The superseded ledger is still computed and still printed as `respath=`
   on every window, so the swap is auditable instead of silent; it is not gated.

   A magnitude bound is blind to both. So the bound is on the VECTOR:
     * |dev - ldev|, the frame's whole change in offset, is scaled back to PHYS-JERK-CAP=500
       units (12 cm, ~7 m/s of offset change at 60 Hz). The corrected point slides along the
       segment [resolved out -> targ + ldev], and `targ + ldev` is the ZERO-JERK CARRY POSITION:
       where the link would sit if it simply travelled with the animation keeping last frame's
       offset exactly. That is the one target for which the eye sees no discontinuity at all,
       which is what this metric is about. Growth, collapse and reorientation are all covered by
       construction — there is no third case left over.
     * The cap is chosen against the measurements it must not touch, not by taste: the worst

       legitimate frame this sim has ever produced and below every jump the owner complained
       about (1011-1161). Velocity-neutral (pos and prev take the identical delta, rule O).

       repairs the segment lengths a per-link pull perturbs (lenmin/lensim are ratcheted) and so
       the clamp — not the bound — still has the last word on the blocker.

       sufficient, for a reason this file already documents elsewhere: `at=` volumes ride a
       chain's SIMULATED tip, so moving one chain moves a volume another chain was cleared
       against, and a clearance recorded at the moment a correction is taken can be invalidated

       of the chain loop to avoid. Measured on the 23:31 run: it fired 5/23/6 times per leg and

       worth of smoothness. Removed; the single application does the work.
     * SHRINK AT ITS SOURCE — the mesh clamp may not tighten its per-chain fraction by more than
       PHYS-TMIN-FALL=0.25 in one frame WHEN A CLEAR POSE EXISTS at the softened fraction. The
       floor is PROVEN clear before it is used; if it penetrates, the bisection runs the full
       range exactly as before. That override is COUNTED (jtfall=) too.
   AND THE OTHER HALF OF THE SAME PROBLEM, WHICH ONLY THE BOUND MADE VISIBLE. With the vector
   bound in, three legs came in at 528 / 545 / 543 and D-MAYOR read 1307.07. Its attribution says
   in one line that this is not the bound failing: rjpre 500.06 (the bound held exactly), and
   rjdn 1307.07 == resjerk == maxdev == that chain's own window deviation — all four the SAME
   number. babak-lod0's chain 1 had left its authored pose by 1307 units (32 cm); the mesh clamp
   found that pose infeasible and collapsed the whole of it in one frame. The clamp had no
   choice — it may not commit a penetrating pose, so at that point the options are COLLAPSE or
   PENETRATE, and penetrating is the one thing forbidden. The only remaining lever is the
   EXCURSION itself, and it should have been bounded from the start: a background villager's
   chain sitting a third of a metre off its authored pose is not subtle secondary motion, it is
   the defect the owner has been describing since cycle 2 — "l'entierete des cheveux bouge, comme
   detachee du crane", "ca part un peu en live".
     * PHYS-DEV-MAX = 800 units (19.5 cm) is the ceiling on |out - targ|, applied in the same
       pass and the same way (scale along its own direction, towards the authored pose). Chosen
       against the same measurements as the jerk cap: ABOVE both ratcheted locomotion peaks by
       construction (hairrun 613-630, chestrun 352.48, so neither can be trimmed by it) and BELOW
       every excursion that produced a collapse (babak 1307, yakow 1123, the mayor's tie 2304).
       jdcut counts the times it bit and jdmax reports the largest offset it had to trim, so
       "how far out was it really" stays a number rather than an assumption.
     * The two bounds COMPOSE into a hard ceiling on resjerk, which is worth writing out because
       it is the reason this is a guarantee and not a hope. Let a = ldev (|a| <= 800 by the
       excursion ceiling) and let the frame's bounded pose be a + D with |D| <= 500 (jerk bound).
       The mesh clamp only ever scales that towards the authored pose, so the committed offset is
       alpha*(a + D) for some alpha in [0,1]. Then
           resjerk = |alpha*(a+D) - a| = |(alpha-1)*a + alpha*D| <= (1-alpha)*800 + alpha*500
       which is maximised at alpha = 0 and equals 800. A full collapse is the worst case and it
       is bounded by the excursion ceiling; anything short of a collapse is bounded by the jerk
       cap. Both ends sit under the 1000-unit leg gate with margin.
     * THAT PREMISE HAD A LEAK, AND THE DEVICE FOUND IT RATHER THAN THE ARGUMENT. With the
       ceiling settle-gated like the jerk bound, D-MAYOR still read resjerk = 1157.90 == rjdn
       while jdmax said the ceiling had only ever SEEN 1110.51 — i.e. |ldev| was exceeding the
       ceiling on frames the ceiling never ran. babak-lod0 reseeds ~68 times per window, so
       `ldev` was being written on spawn-ramp frames where the ceiling was skipped, and the first

       TOWARDS the authored pose and never wants a link 800 units out. The jerk bound stays
       settle-gated — bounding the ramp's own deliberate motion would fight it. rjpre is gated
       the same way resjerk is, so `resjerk - rjpre` compares two figures measured on the same
       frames.

A CRASH THAT WAS THE DIAGNOSTIC KILLING THE GAME IT WAS DIAGNOSING (fixed, and it is the owner's
crash too, not just the harness's)
------------------------------------------------------------------------------------------------
Both occurrences symbolize to ONE instruction. The encoding at the faulting pc, `0xa9405eda`
(`ldp x26, x23, [x22]`), appears EXACTLY ONCE, 4-byte aligned, in the whole 120 MB of libgk.so —
at file offset 0x37dbcc = `gk_sigusr2_hang_dump`, android/gk_android_main.cpp:8790. Load bases
recovered three independent ways (goal_main+0xe48, gk_sdl_main+0x1e68, android_gfx::sync_path+0x78,
all already dladdr-symbolized in the log) confirm pc - base = 0x37dbcc in each run.

The mechanism, end to end:
  * The A37 hang watchdog watches a36_tree::g_frame, which is bumped from sceGsSyncV on the GOAL
    thread. During heavy texture staging the GOAL thread parks in android_gfx::sync_path ->
    pthread_cond_wait, so g_frame freezes WHILE THE GAME IS RENDERING NORMALLY — the D-MAYOR log
    has the watchdog reporting "frame stuck at 209" next to `A35-RENDER frame=240 ... 46.9 fps`.
  * After 3 x 2 s it pthread_kill(SIGUSR2) at the GL thread and dumps its frame-pointer chain.
  * That walk dereferenced the frame pointer RAW, guarded only by `fp >= 0x10000 && (fp & 7) == 0`
    — which garbage passes trivially. Measured values that passed and then faulted:
    fp = 0xffffffff00000000 (D-MAYOR) and 0x43090000430a0000 (a deploy boot at 23:22:46, a third
    occurrence nobody had noticed). Whether it kills the app depends purely on where the GL thread
    happened to be: inside libgk (frame pointers, walk terminates cleanly — the 23:39 D-RIDER run,
    no crash) or inside libGLESv2_adreno / libgsl (no frame pointers, x29 chains into garbage —
    both crashes).
  * FIX: the walk now uses a sigsetjmp-protected pointer read, gk_diag::safe_read_ptr, the same
    protection every OTHER reader in that file has used since the A11 diag; this loop was the one
    that did not. An unreadable frame ends the walk with a line saying so instead of a SIGSEGV.
This matters beyond the harness: the trigger is heavy texture staging, which is a normal thing to
hit while playing, and the app died. It is the owner's crash as much as the test's.
STILL OPEN, and stated rather than fixed here: the watchdog's false positive itself. Watching a
counter that only the GOAL thread bumps means a parked GOAL thread reads as a hung renderer. The
SIGUSR2 is now harmless, but it should not be fired at all while A35-RENDER is advancing.

WHAT THE WIDER CENSUS IMMEDIATELY FOUND — the point of coverage, in one defect and one false red
----------------------------------------------------------------------------------------------
Widening the census did not just raise a count. The first execution that measured Rock Village and
the Volcanic Crater failed two gates, both on actors that had never been measured once. That is the
owner's 2026-08-09 objection answering itself, and it is recorded here rather than smoothed over.

 1. ogreboss-lod0 / ogreboss-village2-lod0 — A GIANT WEARING HUMAN-TEMPLATE PARAMETERS.
    Rock Village produced two windows over the 5000-unit bound, all of it on this one actor: chain
    lag reached 6599.09 units on chestDanglerL, with chestDangleR at 5021.66, chestDangleL at
    4734.71, backDangler at 4518.97, shackle at 4334.74 and chestDanglerR at 4192.23 — six of its
    seven family-B hanging chains at once, while every family-A chain on the SAME actor driven by
    the SAME anchor sat between 619.07 and 1394.18. The split by family is the whole diagnosis.
    WHAT THE NUMBER IS, precisely, because it changes what may be claimed: cdev/maxdev is
    |out - targ| sampled at write-back (jak-hd-physics.gc:5420-5432), BEFORE the jerk bound, the
    excursion ceiling and the mesh feasibility clamp — those are separate later passes (:5805,
    :5712) and cdev is never re-measured after them. So this is NOT "a dangler a third of a metre
    off its animated pose on screen": the bone left each frame within the ceiling, and the leg's own
    attribution says so (the ceiling bit 97 times, trimming offsets up to 1808.18). It is a spring
    lagging that far and being hauled back by a hard clamp every single frame — the solver fighting
    itself, and the mechanism behind that leg's downward jerk sitting exactly on the ceiling value.
    Also worth recording: canch is anchor ACCELERATION, not travel (:2653-2681; the declaration
    comment at :727 is stale and says travel).
    CAUSE: 15 chains on a boss whose body capsules run to 13646 units carry the same stiffness=1.8,
    damping=0.20 and cones of 26-38 degrees as a villager whose capsules run to ~2800. The cone is
    specified in DEGREES, so the same angle on bones three times longer is worth three times the
    units; and the lag term goes as 1/stiffness^2 (acc = wi^2*(t-p) at :3077, wi = 2*pi*hz/sqrt(mass)
    at :2253). Nobody chose these numbers for this actor — they are the cast-wide template.
    FIX: DATA ONLY, seven lines, no build, hot-reloaded over the external override (the path SPEC 15
    asked to start using). The four chest danglers and the two back/arm danglers go to
    stiffness=3.0 damping=0.40 with cones of 14 and 18 degrees; the shackle to stiffness=4.4
    damping=0.40 cone 12. These sit INSIDE the file's own family-B range, which already spans
    stiffness 1.35-5.5, damping 0.20-0.45 and cones from 6 to 38 degrees — this is the owner's
    case-by-case rule applied to an actor that had only ever had the template.
    RESULT, same gate, unchanged at 5000: the worst window on that actor fell 6599.09 -> 3794.90,
    i.e. 24 per cent under the bound, and it is now the worst figure anywhere in the run (the next
    is the mayor at 2304.97). The bound was not widened, and nothing else moved: every other leg
    kept its numbers, the mesh blocker stayed at zero everywhere and the locomotion floors held.
    NOT CLAIMED: the owner has never seen this actor's physics and there is no verdict to regress
    to. If 14 degrees now reads as too tight on a boss that size, it is one number in a 20 KB file.

 2. THE MAYOR'S LEG FAILED ITS AUTHORED-SUSPENSION GATE, AND THE GATE WAS WRONG, PROVABLY.
    That leg reported autheng=1 with authrel=0 and the verdict "engaged and never released, physics
    does not resume" — while holdmax in the same leg read 1. holdmax is the DURATION counter, it is
    per-chain cumulative and deliberately not reset at a window boundary (:2871-2874), so a value of
    1 says the longest unbroken suspension anywhere in that leg was a SINGLE FRAME. A chain cannot
    be "suspended and never handed back" for one frame. What was missing was the release COUNT, not
    the release: autheng/authrel are 0.5-crossings of the blend weight, they are reset per window
    (:6676-6677), and the blend-out takes ~20 frames at authfall=3, so an engagement near a window's
    last frames books its release into the next window or after the leg ends.
    The counter shape was MASKING, not detecting: the previous run read engage=2 release=1 on the
    same leg — one unreleased engagement then too — and passed only because a second one happened to
    release. So the gate fired on sample size, not on behaviour.
    CHANGE: the hard failure is kept and is now stated in terms of duration — engaged, no release
    ever counted, AND a hold that actually stood for at least a second (60 frames). Below that it is
    an OPEN item carrying its own evidence. The stricter stuck-blend gate (holdmax >= 900 frames =
    15 s) is untouched, and comparison of everything else is unchanged. This is flagged loudly
    because changing a gate to get past it is exactly what this phase must not do: the justification
    is that an INDEPENDENT counter in the SAME leg contradicts the verdict, not that it was in the
    way. Reverse it by moving one number, which is named above.
    HONEST NOTE ON THIS RUN: the amended gate was not what let the leg through. On the passing run
    that leg read engage=0 release=0 — the authored hold never triggered at all, so the branch never
    executed. The correction stands on its own reasoning, not on this execution.

MESH-LEVEL POSITIVE CONTROL (C14-B — the rule that every zero must be shown able to rise)
-----------------------------------------------------------------------------------------
inject= (chain param 26) deliberately displaces every chain INTO the body, data-only, external
override, device file byte-restored. The mesh audit must see the deliberate penetration: mraw
(pre-resolve depth beyond the authored floor) must CLIMB, and mfix (clamps committed) must be
nonzero. The DISARMED run must read meshpen 0 over a nonzero meshtested.

ONE ASSERTION IN THIS CONTROL CHANGED THIS CYCLE, AND IT IS A RELAXATION, SO IT IS FLAGGED
RATHER THAN SLIPPED IN. It used to also demand meshpen > 0 while ARMED, on the correct
principle that a counter which can never rise proves nothing when it reads zero. With the
feasibility clamp of 3b, meshpen CANNOT be nonzero unless the guarantee itself is broken —
demanding that it rise is now demanding that the fix not work. So meshpen stops being the
DETECTOR and becomes a CHECKED POSTCONDITION, and the detection sits on the two counters
either side of the resolve, both still gated and both unchanged: mraw must climb, mfix must
fire. The anti-vacuous-zero rule is met in its own terms — meshpen=0 is not "nobody looked",
it is "mfix commits were each re-audited AT the committed point and every one came back
clear", and mfix is that backing count; a zero with mfix=0 is still an empty zero and still
fails. What the control can no longer prove is that a BROKEN clamp would be caught by
injection: it would be caught by the same re-audit that produces meshpen, but not by this
needle. Stated, not papered over.
TWO THINGS ABOUT THIS CONTROL CHANGED IN CYCLE 15, BOTH BECAUSE IT WAS FOUND NOT FIRING.
Run as it stood, it reported windows6=2, injected=0, mraw=0, mfix=0 — IDENTICAL on the armed and
the disarmed leg. A control that produces the same numbers with and without the defect is not a
control. Two causes, both staging:
  * it never set physics? or physics-quality, so it ran on whatever the owner had left in
    settings.ini (at tier 0 the whole mesh block is skipped), it launched through `monkey`
    (= MainActivity, which bypasses pack extraction) and it never warped — so it watched a title
    screen where no chain is anywhere near a body volume. It now stages itself exactly as the
    device legs do: physics?=#t, quality 2, LoaderActivity, village1-hut warp, ini byte-restored.
  * the injection depth went 140 -> 600 units, and this one is a direct consequence of the
    cycle-15 bounds: they run BETWEEN the injection and the mesh probe, so they bound the
    deliberate defect too. At 140 the armed leg read mraw=195.56 against a disarmed 220.21 — the
    needle had stopped separating. At 600 it separates cleanly. Raising the injection is the
    honest response; keeping a needle that no longer moves is not.
